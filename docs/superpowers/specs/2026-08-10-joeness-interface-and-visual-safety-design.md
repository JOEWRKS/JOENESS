# JOENESS 공개 인터페이스 및 시각 검증 안전성 설계

**작성일:** 2026-08-10
**상태:** 승인된 대화 설계를 구현 명세로 고정
**대상:** JOENESS 0.1 Beta의 다음 호환 업데이트

## 1. 배경

현재 제품명은 `JOENESS`지만 실제 사용 표면에는 다음 이름이 섞여 있다.

- 설치 진입점: `JOENESS-0.1.ps1`, `harness.ps1`, 내부 `sync-harness.ps1`
- 활성 스킬: `$joewrks-project-setup`, `$joewrks-design-frontend`, `$handoff`
- 외부 자료와 플러그인: UI UX Pro Max, Apple Design, Figma, Superpowers, Ponytail
- 내부 상태와 과거 평가: `JOEWRKS-*`, `joewrks-*`, `docs/superpowers/**`, `evals/**`

이 혼재는 사용자가 무엇을 직접 호출해야 하는지, 무엇이 JOENESS가 내부에서 선택하는 도구인지 구분하기 어렵게 만든다. 또한 RVR 실사용 사고는 UI/UX 설계와 시각적 런타임 결함 검증이 서로 다른 책임임을 보여 주었다.

이번 변경은 과거 증거와 외부 원본을 전역 개명하지 않는다. **현재 사용자가 보는 활성 인터페이스만 짧고 일관되게 만들고**, RVR에서 확인된 재발 방지 규칙을 필요한 작업에만 조건부로 추가한다.

## 2. 목표

1. 일반 사용자가 기억할 이름을 설치 파일 하나와 스킬 네 개로 제한한다.
2. 자연어 요청을 기본으로 유지하고, 명시적 호출은 역할을 확실히 고를 때만 사용한다.
3. UI/UX 제작과 시각 결함 검증을 분리한다.
4. 외부 배포 부작용, 산출물 혼동, 성급한 `해결` 판정을 막는다.
5. 현재 설치본에서 안전하게 마이그레이션하고 제거·롤백 계약을 유지한다.
6. 공통 Core는 얇게 유지하고 프로젝트별 세부 규칙을 전역화하지 않는다.

## 3. 비목표

- 과거 평가·실험·사고 문서의 파일명이나 내용을 새 이름으로 다시 쓰지 않는다.
- UI UX Pro Max, Apple Design 및 외부 플러그인의 원본 namespace를 개명하지 않는다.
- Superpowers, Ponytail, Figma의 복제 스킬이나 JOENESS 별칭 스킬을 만들지 않는다.
- 모든 프로젝트에 배포 원장, 상태 행렬, 스크린샷 자동화, 장문의 사고 보고서를 강제하지 않는다.
- JOENESS를 결과물 품질 증폭기로 재정의하지 않는다. 핵심 가치는 사용자 의도 이행, 맥락 유지, 범위 통제, 허위 완료 방지다.

## 4. 공개 이름 계약

### 4.1 제품과 설치 진입점

| 역할 | 새 공개 이름 | 처리 |
|---|---|---|
| 제품 | `JOENESS` | 유일한 제품명 |
| 버전 | manifest의 `release.version` | 파일명과 분리 |
| 대표 설치 파일 | `JOENESS.ps1` | README의 모든 기본 명령에서 사용 |
| 이전 대표 파일 | `JOENESS-0.1.ps1` | 한 호환 기간 동안 얇은 전달 래퍼 유지 |
| 과거 별칭 | `harness.ps1` | 한 호환 기간 동안 얇은 전달 래퍼 유지 |
| 내부 구현 | `scripts/sync-harness.ps1` | 사용자 호출 대상으로 문서화하지 않음 |

`JOENESS.ps1`은 `-Check`, `-Apply`, `-Remove`를 기존과 동일하게 전달한다. 버전이 올라가도 사용 명령은 바뀌지 않는다.

두 호환 래퍼는 0.1 Beta 동안 조용히 같은 구현으로 전달한다. 제거는 이번 변경에 포함하지 않으며, 향후 별도 승인된 릴리스에서만 한다. README의 기본 흐름과 정상 출력에는 옛 이름을 반복 노출하지 않는다.

### 4.2 활성 스킬

| 호출명 | 표시명 | 책임 | 기본 선택 정책 |
|---|---|---|---|
| `$project` | Project | 장기 프로젝트 계약, 단계별 로드맵, 실행·검증·배포 경계 | 좁은 조건에서 자동 선택 가능 |
| `$design` | Design | 의미 있는 UI/UX 설계·구현·검증 라우팅 | 관련 작업에서 자동 선택 가능 |
| `$visual-check` | Visual Check | 시각 결함·거절된 화면·상태별 렌더링 회귀 검증 | 시각 결함 신호가 있을 때만 자동 선택 가능 |
| `$handoff` | Handoff | 작업 인계와 맥락 복구 | 명시 요청 전용 유지 |

사용자는 평소처럼 자연어로 요청한다. `$...` 호출은 특정 역할의 적용을 보장하고 싶을 때만 쓴다. 스킬 출력과 확인 문구는 사용자가 쓰는 언어를 따른다.

### 4.3 이름 경계

- 활성 manifest 키, 설치 디렉터리, `SKILL.md`의 `name`, `openai.yaml`의 기본 프롬프트는 새 호출명과 일치한다.
- 내부 보조 스크립트 `project-setup.ps1`, 기존 상태 파일, 백업 경로, marker 이름, PowerShell 함수명은 호환성 때문에 유지한다.
- 외부 원본명과 플러그인 namespace는 manifest, 라이선스, 고급 출처 안내에만 남긴다.
- 과거 문서에서 옛 호출명을 새 이름으로 치환하지 않는다. 과거 결과는 당시 상태의 증거다.

## 5. 스킬 책임과 라우팅

### 5.1 `$project`

기존 프로젝트 설정 스킬을 짧은 이름으로 승계한다. 작은 단일 작업에는 개입하지 않는다. 장기 프로젝트인데 유효한 계획 원장이 없을 때 한 번 제안하고, 사용자가 승인한 경우에만 파일을 기록한다.

외부 배포가 있는 프로젝트에서는 다음을 프로젝트 계약에 조건부로 기록한다.

- 코드를 만들지만 배포하지 않는 안전한 build/test 명령
- 실제 배포를 수행하는 명령과 대상 위치 또는 시스템
- 배포 전에 멈춰야 하는 조건과 보호해야 하는 실행 프로세스
- 수락 상태와 복원 기준을 기록하는 프로젝트의 기준 문서 위치와 우선순위

최신 수락 증거와 기준 문서가 충돌하면 기준 문서를 자동으로 사실처럼 사용하지 않는다. 어느 쪽이 최신인지 재확인하고, 오래된 문서는 갱신하거나 명시적으로 오래된 상태로 표시한다. 복원 가능한 파일이 있다는 것과 실제 복원이 검증됐다는 것도 구분한다.

외부 배포를 실제 실행할 때는 기록만으로 끝내지 않는다. 실행 직전에 현재 프로젝트 루트와 Git 상태, 배포 명령, 실제 대상, 보호 프로세스를 다시 확인한다. 안전한 무배포 build/test 경로가 필요한데 없다면 임의로 배포 명령을 대신 실행하지 않고 중단한다. 배포 후에는 가능한 경우 실제 대상 파일이나 시스템 상태를 다시 읽어 기대한 산출물 해시와 대조한다.

Git을 사용하지 않는 프로젝트에서는 Git 상태를 요구하지 않는다. 대신 현재 작업 루트와 입력 산출물의 실제 상태를 기준으로 삼는다.

Stardew Valley, SMAPI, 특정 DLL 경로, 특정 프로세스명은 프로젝트 규칙이며 JOENESS 공통 내용이 아니다.

### 5.2 `$design`

의미 있는 UI/UX 설계, 화면 구조, 상호작용, 반응형 구현을 담당한다. 내부에서 UI UX Pro Max와 Apple Design 자료를 필요한 부분만 읽고, 실제 Figma 파일이나 Figma 대조가 작업에 필요한 경우에만 Figma 기능을 사용한다.

기존 화면의 방향 오류, 움직이는 상태에서만 발생하는 렌더링 결함, 잘못 배포된 아티팩트 검증은 `$design`의 단독 책임이 아니다. 디자인 의도 자체도 변경해야 하면 `$design`과 `$visual-check`를 각각 필요한 순서로 사용한다.

### 5.3 `$visual-check`

다음 중 하나가 있을 때만 활성화한다.

- 사용자가 현재 화면·애니메이션·렌더링 결과의 구체적 결함을 보고함
- 사용자가 구현 결과가 명시한 시각 요구나 이전 수락 상태와 다르다고 거절함
- 방향, 동작, 뷰포트, 장치 등 상태 차이를 비교해야 하는 시각 회귀가 있음

새 디자인 탐색, 주관적인 스타일 변경, 첫 시안에 대한 단순 선호 피드백은 `$design`의 책임이다. 시각 요구의 충족 여부나 상태별 회귀를 판별해야 할 때만 `$visual-check`로 보낸다.

작업 계약은 다음과 같다.

1. 사용자가 지목한 정확한 대상과 상태를 원래 실패 상태로 고정한다.
2. 보호할 회귀 상태만 추가한다. 가능한 모든 조합을 전수 행렬로 만들지 않는다.
3. 한 검증 주기에는 한 가설과 그 가설을 판별할 최소한의 실질적 변경 묶음만 둔다. 서로 분리할 수 없는 변경은 이유와 범위를 함께 기록한다.
4. 기각된 가설과 실패한 방법은 새 증거 없이 반복하지 않는다.
5. `소스 검사 → 빌드 산출물 → 실제 배포본 → 시각 후보 → 사용자 수락`을 서로 다른 상태로 기록한다.
6. 자동 검사나 다른 상태의 화면만 통과한 경우 원래 결함을 `해결`로 보고하지 않는다.
7. 재시도와 외부 프로세스 사고는 Interaction Safety Core의 중단 예산을 그대로 따른다.

배포 가능한 산출물이 이후 복원·회귀 기준이 될 때는 해당 프로젝트가 정한 한 증거 포인터에, 적용 가능한 범위에서 `소스 commit과 worktree`, `빌드 산출물 해시`, `실제 배포본 해시`, `사용자가 확인한 정확한 대상과 상태`, `사용자 판정`을 함께 결속한다. `수락됨`, `복원 가능한 사본이 있음`, `복원이 실제 검증됨`은 서로 다른 상태다. 간단한 로컬 UI 수정처럼 이 묶음이 불필요한 작업에는 만들지 않는다.

이 스킬은 범용 배포 도구나 자동 스크린샷 시스템을 소유하지 않는다. 각 프로젝트가 가진 안전한 도구를 사용하고, 없다면 검증되지 않은 층을 정확히 보고한다.

### 5.4 `$handoff`

평상시에는 기존처럼 짧은 인수인계를 유지한다. 반복되는 시각 결함이나 배포 산출물 혼동이 있는 경우에만 다음 필드를 추가한다.

- 현재 실패의 정확한 대상과 상태
- 마지막으로 사용자가 수락한 증거 포인터 또는 적용 가능한 소스·빌드·배포 해시 묶음
- 사용자의 현재 판정
- 이미 기각된 가설과 실패한 방법
- 다음에 검증할 단일 가설

모든 handoff를 사고 보고서로 만들지 않는다.

## 6. 외부 자료와 플러그인 경계

| 구성 | 사용자 관점 | JOENESS 내부 역할 |
|---|---|---|
| UI UX Pro Max | 별도 호출 불필요 | `$design`의 비노출 참고자료 |
| Apple Design | 별도 호출 불필요 | `$design`의 비노출 참고자료 |
| Figma | 필요하면 제품명으로 직접 요구 가능 | 실제 Figma 제작·대조가 필요할 때만 사용 |
| Superpowers | 세부 스킬명 암기 불필요 | 계획·디버깅·테스트 등 해당 작업 절차에 사용 |
| Ponytail | 필요하면 제품명으로 직접 요구 가능 | 최소 구현 또는 과구현 감사에 사용 |

JOENESS는 외부 플러그인의 설치·업데이트를 소유하지 않는다. 기능이 설치되어 있지 않으면 가능한 대체 경로를 사용하고, 중요한 기능 차이가 있으면 정확히 알린다.

## 7. Interaction Safety Core 최소 보강

공통 Core에는 한 가지 의미만 추가한다.

> 이름이 build 또는 test여도 배포 폴더, 공유 대상, 외부 실행 환경을 바꾸면 외부 쓰기로 취급한다.

현재 Core의 크기 제한은 2,048바이트이므로 새 단락을 덧붙이지 않는다. 기존 외부 쓰기 문장을 같은 의미 예산 안에서 다시 써야 한다. 시각 상태 행렬, 배포 세부 절차, 수락 묶음은 Core에 넣지 않는다.

기존 `interaction-safety-core-v1.md`는 당시 활성 규칙의 역사 증거로 보존한다. 보강 문장은 새 `interaction-safety-core-v2.md`에 반영하고 manifest의 `activeCommonCore`만 새 파일로 전환한다.

## 8. 설치 마이그레이션

### 8.1 새 설치

manifest의 활성 스킬은 정확히 `project`, `design`, `visual-check`, `handoff`가 된다. 디자인 vendor 의존성은 `design`에만 연결한다.

이름 변경이나 새 스킬 추가만으로 품질 승격을 주장하지 않는다. 네 스킬은 실제 새 작업 smoke test와 새 행동 평가가 끝날 때까지 `candidate` 상태를 유지한다.

설치 결과의 공개 JSON도 역할 중립적인 이름을 사용한다. 최소 공개 필드는 `status`, `mode`, `agentsRoot`, `skillsRoot`, `activeSkills`, `changes`, `warnings`로 정리한다. `designFrontendRoot`, `designFrontendPilot`, `designFrontend`, `personal-pilot`은 새 정상 출력에서 제거한다. 폐기된 `-IncludeDesignFrontend` 입력은 0.1 Beta 호환 기간에는 무시되는 파라미터로만 받고, 특정 옛 스킬명을 반복하지 않는 간결한 폐기 경고를 반환한다.

### 8.2 기존 설치 업데이트

1. 현재 설치 state가 소유한 옛 스킬 파일의 해시를 확인한다.
2. 옛 파일이 설치 당시와 같을 때만 제거하고 새 디렉터리에 설치한다.
3. 사용자가 수정한 옛 파일, 비소유 파일, 새 이름 충돌이 있으면 쓰기 전에 중단한다.
4. `.agents/skills`와 호환 검사 대상 skill root 전체에서 `project`, `design`, `visual-check`, `handoff` 이름 충돌을 검사한다.
5. 옛 이름의 별칭 스킬은 설치하지 않는다. 중복 발견과 이중 라우팅을 막기 위해 하드 컷한다.

충돌 검사는 두 종류를 구분한다.

- 새 스킬의 정확한 설치 대상 디렉터리에 비소유 내용이 있으면 `SKILL.md` 유무와 관계없이 쓰기 전에 중단한다.
- 다른 skill root의 충돌은 실제 `SKILL.md` frontmatter 이름을 읽어 판정한다. 단순히 같은 이름의 일반 디렉터리가 있다는 이유로 충돌 처리하지 않는다.

다른 root에 비소유 옛 `$joewrks-project-setup` 또는 `$joewrks-design-frontend`가 남아 있으면 JOENESS가 임의 삭제하지 않고, 이중 라우팅을 막기 위해 위치를 보고하고 쓰기 전에 중단한다.

열려 있는 Codex 작업은 시작 시 주입된 스킬 목록을 소급 갱신하지 못한다. `-Apply` 성공 뒤 새 작업 또는 앱 재로딩에서 새 이름을 검증해야 한다.

### 8.3 역사와 내부 호환

다음은 그대로 보존한다.

- `docs/superpowers/**`, `evals/**`, 과거 candidate와 experiment
- vendor 원본 경로, 원본명, 라이선스, upstream identity
- `JOEWRKS-HARNESS` 및 프로젝트 marker
- 설치 state 파일명, 백업 경로, 내부 함수명
- 과거 behavior evidence와 평가 포인터

옛 디자인 라우터 평가를 이름만 바꿔 현재 스킬의 검증 증거로 재사용하지 않는다. 기존 결과는 역사로 남기고, 새 이름과 새 라우팅 경계를 검증한 결과는 별도 artifact로 추가한다.

현재 설치기는 state schema V1을 읽을 때 활성 `joewrks-design-frontend` descriptor와 당시 Core 바이트를 참조한다. 활성 키를 `design`으로 바꾸기 전에 이 정확한 역사 자료를 manifest의 비활성 `compatibility.legacyInstallSources` 영역과 비발견 source 경로로 이동한다. 이 영역은 V1 설치 검증·제거·마이그레이션에만 사용하며 새 설치 선택에는 포함하지 않는다. 역사 바이트와 SHA-256은 기존 값과 정확히 일치해야 한다.

manifest의 옛 `evaluation.current`는 새 활성 스킬의 현재 검증인 것처럼 남겨 두지 않는다. 기존 라우터 결과는 history로 보존하고, 새 현재 평가는 `candidate/unvalidated`에서 시작해 새 artifact가 생성된 뒤에만 그 포인터를 갱신한다.

### 8.4 디렉터리와 롤백

정상 마이그레이션·제거 또는 실패 롤백에서는 이번 실행이 만들었거나 관리 파일 제거로 비게 된 디렉터리만 가장 깊은 경로부터 검사해 제거한다. 검증 시점에 내용이 하나라도 남아 있으면 디렉터리를 삭제하지 않는다. 외부 파일을 지우거나, 경로 이름만 보고 재귀 삭제하지 않는다.

`롤백`은 한 번의 `-Apply` 실행이 실패했을 때 시작 전 파일 상태로 복구하는 트랜잭션 롤백을 뜻한다. 이전 JOENESS 릴리스로 되돌리는 release downgrade와 구분한다. downgrade는 이전 checkout의 직접 적용이 안전한지 회귀 검사하고, 통과하지 않으면 `현재 릴리스 -Remove → 이전 릴리스 -Apply` 절차만 문서화한다. 검증 전에는 직접 downgrade 지원을 주장하지 않는다.

## 9. README 구조

일반 사용자가 처음 보는 구간에는 다음만 둔다.

1. `JOENESS.ps1 -Check`
2. `JOENESS.ps1 -Apply`
3. 앱 재실행 또는 새 작업
4. 자연어로 작업 요청
5. 필요할 때만 네 호출명 사용

외부 플러그인과 vendor는 `설치 구성과 출처` 구간에서 역할·설치 주체·대체 가능 여부를 짧게 설명한다. 옛 호출명은 한 번의 마이그레이션 표에만 남긴다. 한국어와 영어 안내는 같은 정보를 제공한다.

## 10. 검증 전략

### 10.1 무결성과 설치

- 대표 진입점이 `JOENESS.ps1`이고 manifest 버전과 분리되어 있는지 검사
- 새 설치의 활성 스킬이 네 개와 정확히 일치하는지 검사
- 모든 manifest 파일의 바이트와 SHA-256 검사
- 현재 0.1 설치본에서 새 이름으로 정상 마이그레이션되는지 검사
- state schema V1 설치본이 비활성 역사 source를 통해 정상 마이그레이션되는지 검사
- drift가 있는 옛 파일과 비소유 충돌에서 쓰기 전 중단하는지 검사
- `-Check`, `-Apply`, `-Remove`, 두 호환 래퍼, 실패 롤백 검사
- 제거 후 JOENESS 소유 파일만 사라지는지 검사
- 성공·제거·실패 롤백 후 이번 실행이 만든 빈 디렉터리만 정리되는지 검사
- 공개 JSON에 옛 `designFrontend...`·`personal-pilot` 필드가 남지 않는지 검사
- 이전 릴리스 직접 적용 downgrade 가능 여부를 검사하고 실패 시 안전한 제거 후 재설치 절차를 확인

### 10.2 라우팅

- 새 장기 앱 프로젝트이며 계획 원장이 없음 → `project`
- 작은 파일 수정 → `project` 미선택
- 로그인 화면 설계·구현 → `design`
- 걷는 방향에서만 프레임이 뒤집힘 → `visual-check`, `design` 단독 미선택
- 시각 결함을 고치면서 디자인 의도도 변경 → 두 역할을 구분해 순서대로 사용
- 첫 시안이 단순히 마음에 들지 않음 → `design`, `visual-check` 미선택
- 다음 작업에 넘길 요약 요청 → 명시적 `handoff`
- 일반 상태 보고 → `handoff` 자동 선택 안 함

### 10.3 RVR 회귀 시나리오

- build가 외부 배포 폴더를 바꾸면 외부 쓰기로 분류
- 자동 검사 통과·시각 실패 상태에서 `해결` 보고 금지
- 정지 상태의 성공을 이동 상태 성공으로 일반화하지 않음
- 같은 commit이라도 실제 배포 해시가 다르면 동일 산출물로 보지 않음
- 새 증거 없이 기각된 가설을 반복하지 않음
- handoff가 마지막 수락 해시와 다음 단일 가설을 보존
- 오래된 기준 문서와 최신 수락 원장이 충돌하면 현재 Git·실제 배포본·해시·직접 검증을 먼저 읽고 `불일치/미확인`으로 표시한 뒤, 증거가 확정된 후에만 기준 문서를 갱신

### 10.4 언어와 실제 노출

- 실패 영수증, 확인 필요 블록, 다음 단계가 사용자 언어로 출력되는지 검사
- 현재 작업이 아닌 새 Codex 작업에서 `$project`, `$design`, `$visual-check`, `$handoff` 노출과 호출을 실제 확인
- 외부 provider namespace가 JOENESS 기본 사용법에 노출되지 않는지 검사

과거 실험 파일은 수정하지 않는다. 새 행동 검증 결과는 새 artifact로 기록한다.

## 11. 합격 기준

- 사용자가 기억할 공개 이름이 `JOENESS.ps1`과 네 호출명으로 정리된다.
- README 기본 흐름에서 옛 이름과 외부 provider 세부 호출명이 제거된다.
- 새 설치와 기존 설치 마이그레이션이 모두 원자적이고 drift-safe하다.
- V1 호환 자료는 비활성 경계에 남아 있지만 새 설치와 사용자 호출 목록에는 노출되지 않는다.
- UI/UX 제작과 시각 결함 검증이 라우팅 검사에서 혼동되지 않는다.
- 빌드 이름 아래 숨은 외부 배포가 공통 안전 규칙을 우회하지 못한다.
- 자동검사나 다른 상태의 증거만으로 원래 시각 결함을 해결했다고 보고하지 않는다.
- 작은 작업과 정상적인 디자인 작업에는 새 시각 절차의 토큰·문서 비용이 추가되지 않는다.
- 과거 증거, 외부 원본, 내부 제거·롤백 호환성이 유지된다.

## 12. 구현 순서

1. 이름·진입점·manifest 계약에 대한 실패 검사를 먼저 작성한다.
2. 스킬 디렉터리와 활성 manifest를 새 공개 이름으로 바꾼다.
3. 기존 설치 마이그레이션과 충돌 검사를 보강한다.
4. `$visual-check`를 최소 조건부 스킬로 추가하고 기존 두 스킬의 경계를 조정한다.
5. Core의 외부 쓰기 문장을 바이트 예산 안에서 보강한다.
6. README 한국어·영어와 마이그레이션 안내를 정리한다.
7. 작은 관련 검사부터 통과시킨 뒤 전체 문서화된 suite를 실행한다.
8. 격리된 임시 홈에 설치하고 새 Codex 작업에서 실제 호출 smoke test를 수행한다.
