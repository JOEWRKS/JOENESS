# JOENESS — 역할 기반 맥락 저장·조회 설계

> 상태: 구현 전 설계. 이 문서는 기존 `joeness-setup`의 저장·조회 계약을 보강한다. 개인 설치, 실제 프로젝트 문서, 런타임 스킬은 이 문서 작성으로 변경되지 않는다.

## 목적과 성공 기준

JOENESS의 제1목표는 새 에이전트가 프로젝트의 목적, 현재 사실, 승인된 결정, 미해결 문제와 다음 행동을 적은 읽기로 정확히 찾고 이어받게 하는 것이다. 사람이 같은 기록을 보고 완료·미완료를 판단할 수 있어야 한다는 목표도 중요하지만, 이를 위해 정보를 중복 저장하거나 실행 맥락을 불필요하게 늘리지 않는다.

성공은 문서 다섯 개의 생성이나 보고 양식 준수가 아니라 다음으로 판단한다.

- 작업에 필요한 최신 사실과 근거를 찾고, 오래된 인수인계보다 현재 파일·Git·대상 상태를 우선한다.
- 중요한 결정·진행·문제·검증 경계를 빠뜨리지 않고 각 사실의 주된 저장 위치를 하나로 유지한다.
- 새 담당자와 사용자가 목표, 한 일, 남은 일, 다음 행동, 승인 여부를 구분한다.
- 무관한 문서 읽기·반복 기록·불필요한 재검증을 늘리지 않는다.

## 제품 경계

활성 제품은 기존 얇은 Independent Judgment Core와 공개 `joeness-setup` 스킬 하나를 유지한다. Core에 기록 규칙을 추가하지 않는다. 별도 메모리 DB, 백그라운드 수집기, 문서별 에이전트, 새로운 공개 스킬, 일괄 문서 변환기는 만들지 않는다. `.joeness/setup-state.json`은 AGENTS 관리 구역의 적용 기준일 뿐 프로젝트 업무 메모리가 아니다. 기존 Product authority와 승인된 DESIGN authority는 이 설계로 대체하지 않는다.

다섯 가지는 **문서 역할**이지 필수 파일명이나 필수 생성 목록이 아니다. 기존 `TASKS.md`, 추적기, 기획서 등에서 역할이 충족되면 실제 경로를 연결한다. 새 프로젝트도 필요한 역할이 생길 때 최소 문서를 만든다. 사용자의 일반 질문, 토론, 기록 금지 요청은 자동 기록 근거가 아니다.

## 역할과 단일 저장 위치

| 역할 | 주로 보유하는 사실 | 보유하지 않는 것 |
|---|---|---|
| AGENTS | 짧은 상시 안내: 자료 위치, 작업별 읽기 선택, 기록 경계 | 과거 작업 전문, 다섯 문서의 복사본, 장문의 방법론 |
| ROADMAP | 승인된 목표·단계·우선순위, 필수 항목의 상태·완료 근거, 다음 우선순위 | 일별 실행 로그, 검증되지 않은 완료 선언 |
| TASK | 승인된 작업의 진행·결과·검증·재개 지점 | 새 제품 방향, 반복 가능한 문제 원인의 상세 원본 |
| ISSUES | 재발·인수인계 가치가 있는 문제의 증상·원인/가설·해결/우회·잔여 위험 | 모든 일회성 오류와 일반 작업 로그 |
| DESIGN | 승인된 디자인 기준의 원본·버전·적용 범위·미승인 영역 | 새 디자인 승인 창출, Product 결정의 대체 |

Product/UX 원본, 코드, 배포 대상, 사용자 승인 기록은 각자의 권위를 유지한다. 이 다섯 역할에 없는 원본을 억지로 이동하지 않는다. 기록할 사실마다 먼저 **주된 원본 한 곳**을 정하고, 다른 문서가 필요로 하면 짧은 상태와 정확한 항목·경로를 링크한다. 동일한 설명을 여러 문서에 다시 적지 않는다. 링크 대상이 없거나 확인되지 않으면 있는 척하지 않는다.

예를 들어 버그 수정의 실행·테스트 결과는 TASK에, 재발 가능한 원인과 우회는 ISSUES에 쓴다. 그 버그가 ROADMAP 필수 항목을 해소했다면 실제 근거를 확인한 뒤 해당 항목 상태만 갱신한다. 각 문서가 독립된 벽이 아니라 서로의 정확한 원본을 가리키는 구조다.

## 쓰기·간결화 계약

새 기록은 처음부터 짧게 쓴다. 최소 단위는 **사실/결정, 현재 상태, 근거 또는 출처, 남은 행동** 중 해당하는 것뿐이다. 날짜·식별자·검증 결과는 사실을 재찾거나 구별하는 데 필요할 때 남긴다. 설명을 길게 쓴 뒤 별도 AI 요약 단계로 재가공하는 상시 절차는 두지 않는다. 짧게 쓰기 위해 실패 원인, 검증 한계, 승인 경계를 생략하지 않는다.

작업 종료 보고는 이미 확인하고 기록한 사실에서 직접 만든다. 보고 형식 때문에 추가 파일을 생성하거나 모든 문서를 다시 읽고 테스트하지 않는다. 파일을 바꾸지 않았으면 변경했다고 말하지 않는다. 구현 완료, 검증 완료, 사용자 수용은 별도 상태다. 진행 중인 사실을 오래된 ROADMAP이나 인수인계가 덮어쓰지 못한다.

해결된 오래된 상세를 줄일 때는 최신 내용이 실제로 복원되는 정확한 Git 커밋·당시 경로·항목을 먼저 확인한다. 그 뒤 현재 문서에 조회 단서를 남긴다. 미커밋 또는 마지막 커밋 이후의 내용, 활성 문제와 유효한 우회는 보존한다. 복원 근거가 없으면 압축·삭제하지 않는다. 버전 정리 자체가 commit·push 권한을 만들지 않는다.

## 읽기 선택과 권위

AGENTS는 항상 짧은 위치 안내만 제공하고, 나머지는 요청에 맞춰 읽는다. 고정된 `1→5` 순서나 문서에 대한 RACI 표를 두지 않는다. RACI는 사람의 책임·승인 설명에 쓰일 수 있으나 문서 간 사실 권위를 대체하지 않는다.

| 요청 | 우선 찾을 역할 | 조건부로 이어서 찾을 역할 |
|---|---|---|
| 새 작업·재개 | 현재 ROADMAP 단계와 TASK 재개 지점 | 관련 ISSUES, Product/Design 원본 |
| 오류 조사 | 현재 코드·재현 결과와 TASK | 같은 증상의 ISSUES, 단계 영향 시 ROADMAP |
| 목표·완료 판단 | 승인된 Product/ROADMAP 및 필수 항목 근거 | TASK 검증, 관련 ISSUE, 사용자 수용 기록 |
| 시각 작업 | 승인된 DESIGN 원본과 범위, Product 원본 | 관련 ROADMAP/TASK와 실제 렌더 증거 |
| 과거 문제 조회 | ISSUES의 조회 단서 | 가리킨 TASK·Git 이력의 해당 항목 |

이 표는 탐색 출발점이며 모든 행의 문서를 무조건 읽으라는 뜻이 아니다. 규범적 권위(사용자의 명시적 결정, 승인된 Product/Design)와 현재 상태의 관찰 근거(현재 파일·Git·대상)를 구분한다. 최신 관찰은 오래된 상태 서술보다 우선하지만 승인된 범위나 제품 의미를 자동 변경하지 않는다. 충돌하면 출처와 차이를 드러내고 필요한 권한 결정을 요청한다. 옛 계획은 단서로만 쓰며 완료된 일을 반복하거나 새 범위를 추론하지 않는다.

## 기존 문서 재편 제안 기준

기존 문서가 크다는 이유만으로 이동하지 않는다. 아래 기준은 **읽기 전용 조사와 제안의 발동 조건**이며 자동 재편 승인이나 실패 판정이 아니다.

- 즉시 조사: 관찰 가능한 지침 로더 한도를 넘어 실제 잘림이 확인됨; 또는 문서 구조 때문에 현재 상태·승인 범위·다음 행동을 잘못 찾은 구체 사례가 재현됨.
- 그 외에는 다음 약한 신호 중 둘 이상: 상시 읽는 지침이 관찰/설정된 한도의 75% 이상; 한 역할의 권위가 여러 문서에 흩어져 모순됨; 평범한 작업에 무관한 긴 자료를 항상 읽어야 함; 반복되는 사실의 주된 저장 위치가 없거나 중복됨; 새 담당자나 사용자가 문서만으로 완료·미완료·다음 행동을 찾지 못함.

75%는 조기 점검을 위한 임시 기준이지 공식 정상 길이나 자동 변경 경계가 아니다. 한도를 알 수 없으면 비율 신호를 사용하지 않는다. 단일 작은 충돌은 국소 수정이 더 적절할 수 있다. 제안에는 관찰된 증거, 영향을 받은 경로, 현 역할→권장 역할의 매핑, 유지할 승인·출처·이력, 예상 읽기 비용과 변경 범위를 적는다. 사용자가 선택하기 전에는 사용자 소유 문서를 이동·삭제·덮어쓰지 않는다.

재편이 승인되면 기존 원본을 먼저 대조하고 필요한 사실을 분류한다. 중복 문장은 하나의 원본으로 합치되 서로 다른 결정이나 시점은 합치지 않는다. 기존 링크·승인·검증 근거가 살아 있는지 확인한다. 적용 후 새 담당자가 목적·현재 단계·열린 항목·다음 행동을 찾는지 검사한다. 실패나 부분 적용은 숨기지 않고 기존 자료를 보존한다.

## 구현·검증으로 넘길 계약

후속 구현 계획은 현재 `joeness-setup`의 SKILL, 짧은 AGENTS 자산, 필요한 역할별 예시와 사용 안내만 최소 변경 대상으로 삼는다. 실제 프로젝트에 긴 설계 문서를 복사하지 않는다. 관리 구역 소유권 검사·설치 포인터·Independent Judgment Core는 유지한다. 기존 프로젝트 재편은 별도 사용자 승인 대상이며 이번 제품 변경만으로 실행하지 않는다.

검증은 (1) 계약 테스트로 단일 공개 스킬·패키지 경계·짧은 연결을 확인하고, (2) 가상 프로젝트에서 새 기록의 저장 위치, 중복 방지, 필요한 문서만 읽기, 오래된 인수인계와 현재 상태 충돌, 미보존 이력, 부분 실패를 확인하며, (3) 신선한 인수인계에서 목표·한 일·남은 일·다음 행동과 승인 경계를 복원하는지 본다. 복잡도 기준은 잘림/오류 1개 또는 약한 신호 2개일 때 **제안만** 나오는지, 해당하지 않을 때 재편을 강요하지 않는지 확인한다. 동일한 과제에서 토큰·시간을 비교할 수 있으면 비용도 별도로 기록한다. 정적 계약 통과만으로 실제 행동·토큰 절감·사람 사용성을 주장하지 않는다.

이 설계는 새 기능이 완료됐다는 선언이 아니다. 구현 계획과 검증 범위는 이 문서의 사용자 검토 뒤 확정한다.
