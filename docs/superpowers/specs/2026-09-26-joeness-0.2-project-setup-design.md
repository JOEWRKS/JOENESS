# JOENESS 0.2 Project Setup — 구현 설계 명세

> 상태: 사용자 승인 후 구현 중. 아래 구현 기준 정정이 과거 로컬 상태 설명보다 우선한다. 개인 설치·실제 프로젝트 적용·배포는 수행하지 않는다.

## 구현 기준 정정 (2026-09-26)

### 후속 승인: current-only 분리

사용자 승인에 따라 사용자 안내는 현재 제품의 설치·사용·제거만 다룬다. 이전 릴리스 전용 자동 이관과 무효 호환 옵션은 제거한다. 설치 상태의 release/manifest identity는 현재 패키지와 정확히 일치해야 하며, 불일치 시 버전별 전환 안내 없이 파일을 보존하고 일반 충돌을 반환한다. 아래 초기에 결정한 직전 0.2 이관 항목은 이 후속 결정으로 대체되었다. 과거 설계·실패·검증 자료는 개발 기록으로 보존하며 현재 소스에 역사 복사본을 추가하지 않는다.

원격 main `ab3460fd28952baa5c2ad472eed1dd6196054d8e`는 이미 Independent Judgment로 전환하고 0.1 현행 소스를 Git 이력으로 정리했다. 아래 초안의 “현재 0.1” 설명은 오래된 로컬 checkout 관찰이다.

- 승인 Core를 새 경로에 복제하지 않고 `astra-judgment-core.md`의 bytes/hash를 유지한다.
- 단일 공개 진입점은 현재 원격의 `JOENESS.ps1`을 유지한다. 패키지 버전 `0.2`, public skill은 `joeness-setup` 하나다.
- 기존 원격 정리를 반복하지 않는다. 0.1 소스는 원격 main ancestry에서 확인했고 추가 원격 tag/push를 하지 않는다.
- 이관 범위는 exact 직전 `0.2-astra-judgment` 설치다. 0.1/unknown 설치는 무변경 차단하고 해당 historical installer를 통한 소유 확인/제거를 안내한다. 원격 main이 제거한 광범위한 legacy migration을 되살리지 않는 구현상 축소이며, 0.1 자동 이관 완료를 주장하지 않는다.
- 새 릴리스에 맞춰 repository AGENTS의 제품 identity와 current-tree 테스트 allowlist만 갱신한다. Core에 새 행동 규칙을 넣지 않는다.
- 구현·실행 결과와 남은 검증 경계는 `evals/joeness-setup/runs/2026-09-26-implementation/review-evidence.json`에 구분한다. 초기 설계/실패 관찰은 지우지 않는다.
- 독립 리뷰에서 Windows clone의 LF/CRLF 변환 오인을 재현했다. 적용 기준의 예외는 현재/적용 본문이 LF/CRLF만 다르고, 커밋된 AGENTS 구역과 상태 파일이 같은 기준을 확인해 주는 경우로 한정한다. 실제 본문 변경은 계속 edited이며 외부 사용자 bytes는 그대로 보존한다. 실제 Git clone 회귀 테스트로 검증한다.

## 목적과 결정

사용자는 프로젝트를 한 번 세팅한 뒤 평소처럼 작업을 요청한다. 에이전트는 현재 프로젝트 상태와 필요한 원본 자료를 확인하고, 승인된 일의 진행과 중요한 문제 해결 맥락만 담당 문서에 남긴다. 사용자가 매번 기록 파일을 지정할 필요는 없지만, 세팅 승인만으로 제품 구현·외부 설치·전역 변경·commit·push 권한이 생기지 않는다.

이 설계는 사용자가 제공한 `JOENESS_PROJECT_SETUP_MASTER_SPEC_2026-09-26.md`의 기능 경계를 따른다. 추가로 이번 대화에서 결정한 배포 경계는 다음과 같다.

- 현행 0.2 활성 구성은 **얇은 Common Core + 선택형 `joeness-setup` 스킬 하나**다.
- 0.1의 `joewrks-project-setup`을 확장하지 않는다. `handoff`, `joewrks-design-frontend`, `joewrks-project-setup`도 0.2 활성 스킬로 이월하지 않는다.
- 0.1 최종 소스는 GitHub의 확인 가능한 커밋·태그로 보존하고, 0.2 현행 소스 경로에서는 옛 스킬을 제거한다. 기존 실패·실험 보고와 역사적 후보는 삭제하지 않는다.
- 0.1에서 유용한 바이트 보존·스냅샷 검사·복구 테스트는 새 설계의 구현 참고로만 사용한다. 0.1 스크립트나 하네스 전체를 0.2의 런타임 의존성으로 남기지 않는다.
- 0.2의 얇은 Core는 통합 원문과 사용자가 제공한 `Independent Judgment` 본문이다. 그 본문을 확대하거나 프로젝트 문서에 복제하지 않는다. `vendor/source-manifest.json#activeCommonCore`는 계속 단일 설치 포인터로 사용하되, 현재 0.1 포인터를 미래 0.2의 내용 기준으로 자동 채택하지 않는다.

2026-09-26 보완 검토에서 이전 문장의 오류를 확인했다. 현재 manifest는 재시도·프로세스 중단·증거 보고 등을 포함한 `interaction-safety-core-v1.md`를 가리키지만, 통합 원문 §2.1과 사용자 제공 지침은 `Independent Judgment`를 지정한다. 읽기 확인한 개인 AGENTS의 관리 구역도 후자와 일치한다. 다음 구현에서는 승인된 본문만 패키지 소스로 고정하고 hash를 계산한다. 이번 문서 보완은 실제 Core 파일·manifest·개인 설치본을 변경하지 않는다.

기존 `JOENESS-v0.1.0-beta.1` 태그는 원격에 있으나 현재 0.1 스킬 소스는 그 태그 이후에도 변경됐다. 따라서 **제거 직전 기준 커밋을 별도 원격 태그로 확인**해야 최신 0.1 상태를 잃지 않는다. 태그·push는 구현/배포 단계의 별도 행위이며 이 명세 작성으로 수행하지 않는다.

## 0.2 패키지 경계

0.2는 현재 저장소에서 별도 릴리스 식별자를 갖는다. 공개 진입점은 `JOENESS-0.2.ps1` 하나이며, manifest의 릴리스 버전·진입점·정확한 파일 hash가 그 파일과 일치해야 한다. `JOENESS-0.1.ps1`, 0.1 스킬 소스, 오래된 활성 스킬 참조는 0.2 배포 경로에서 제거하고 이전 Git 태그에서만 조회 가능하게 한다. `README.md`는 현재 버전의 설치·제거와 한계를 설명하며, 0.1 사용법을 현행 명령으로 제시하지 않는다.

0.2 설치 대상은 얇은 Core와 `joeness-setup`의 검증된 파일뿐이다. 옛 디자인 라우터·벤더 묶음·추가 public skill은 설치하지 않는다. 이 저장소의 과거 실험 자료가 Git에 남는 것과 0.2 런타임에 포함되는 것은 다르다.

설치·프로젝트 적용·일상 기록·프로젝트 적용 해제·도구 제거는 서로 다른 작업이다. 설치가 프로젝트 문서를 자동 수정하지 않으며, 도구 제거가 이미 적용된 프로젝트 기록이나 운영 연결을 자동 삭제하지 않는다. 개인 설치본은 저장소에서 소스를 지우는 것만으로 사라지지 않는다.

0.1 설치본에서 0.2로 전환할 때는 기존 설치 상태 파일과 manifest로 **소유가 확인된 대상만** 이관한다. 기존 대상이 변경됐거나 소유 증거가 불충분하면 삭제·덮어쓰기를 멈추고 정확한 경로와 충돌을 보고한다. 이관 전 백업, 적용 후 재읽기, 실패 시 복구 또는 부분 상태 보고가 필수다. 사용자 프로젝트 파일에는 이 설치 이관을 적용하지 않는다.

초기 지원 범위는 저장소의 기존 PowerShell 기반 Windows Codex 설치 경로다. 앱·CLI에서의 실제 스킬 발견, 자연어 선택, 재로딩 방법은 검증 결과가 있을 때만 배포 문구로 확정한다. 다른 OS·런타임 지원은 주장하지 않는다.

## 새 스킬 구조와 책임

```text
skills/joeness-setup/
  SKILL.md                 선택 조건, 조사·변경안·승인·적용·일상 기록 경계
  agents/openai.yaml       표시명과 자연어/명시 호출 metadata
  assets/                  AGENTS, ROADMAP, TASK, ISSUES, DESIGN의 작은 형식 참고
  scripts/project-setup.ps1  프로젝트 AGENTS의 소유 구역만 다루는 보조 도구
```

`assets/`는 모든 프로젝트에 복사하는 완제품이 아니다. 동일 역할의 기존 문서와 실제 경로를 우선한다. `SKILL.md`는 통합 설계서 전문이나 옛 하네스 규칙을 싣지 않고, 일할 때 필요한 선택·쓰기 계약만 담는다. 별도 daemon, hook, MCP, DB, 문서별 에이전트, 스킬 라우터를 만들지 않는다.

스킬은 분명한 프로젝트 세팅·재세팅 의도에만 자연어로 선택 가능하다. 명시 호출은 대안으로 제공한다. 작은 수정·질문·오류 조사·일반 작업 요청만으로 세팅을 시작하지 않는다. 세팅 선택은 곧 파일 쓰기 승인이 아니다.

### C1 — 세팅에서 새 세션의 운영까지

세팅 결과에는 실제 원본 경로와 짧은 읽기·기록 약속이 남아야 한다. 일상 작업은 그 프로젝트 지침으로 이어지며 이전 세팅 대화나 매번의 스킬 재호출에 의존하지 않는다. 적용 변경안에는 승인된 업무의 로컬 진행·문제 기록이 기본 동작임을 알린다. 정상 기록마다 승인을 반복하지 않고, 현황 질문·검토 의견·기록 제한은 각 요청의 쓰기 경계를 따른다.

`assets/AGENTS.md`는 존재하는 원본의 역할·실제 경로, 요청 관련 부분만 읽기, 현재 상태 대조, 담당 원본만 갱신, 실행과 기록 실패 구분을 짧게 제시한다. 없는 자료는 실제 링크인 것처럼 쓰지 않는다. 제안서의 설명·시험표를 런타임 지침에 복사하지 않는다.

행동 검증에는 세팅 대화가 없는 새 컨텍스트를 사용한다. 정상 런타임 지침과 적용된 프로젝트만 제공하며 평가용 기대 답안을 주입하지 않는다. 실제 읽기·파일 diff·결과 보고로 기록과 비기록을 확인한다. metadata 값이나 한 번의 성공으로 모든 표현·런타임에서의 실행을 보장하지 않는다.

## 프로젝트 문서 계약

| 역할 | 원본 책임 | 생성·갱신 경계 |
|---|---|---|
| ROADMAP | 목표·범위·비목표·우선순위·단계·완료 기준 | 명확한 결정 또는 근거 있는 상태 변화에만 갱신 |
| TASK | 실제 수행·검증·현재 작업 재개 지점 | 작업 사실이 변했을 때 갱신; 미래 개발 방향을 새로 정하지 않음 |
| ISSUES | 중요한 문제의 원인/가설·시도·해결/우회·잔여 위험 | 인수인계·재발 방지 가치가 있을 때만 생성·갱신 |
| AGENTS | 프로젝트 고유 약속·검증 명령·자료 경로와 선택 기준 | 짧은 연결만; 전체 이력이나 Core를 복제하지 않음 |
| DESIGN | 승인 시각 기준·범위·실제 원본/자산·허용 스킬 연결 | UI/시각 기준이 필요할 때만; 제안은 승인으로 승격하지 않음 |

다섯 파일을 의무적으로 만들지 않는다. 기존 `TASKS.md`, `docs/design.md`, 기획서 또는 추적기가 같은 역할을 담당하면 그 경로를 재사용하고 중복 원본을 만들지 않는다. `STATE.md`를 추가하지 않는다. 목표의 완료 조건과 코드 수정·테스트 통과·사용자 검수·배포 상태를 섞지 않는다.

### C2 — 버전별 보존·이월·조회

사용자 프로젝트의 버전 정리는 요청이나 확인된 마일스톤 전환에 따른 선택적 작업이다. 버전마다 자동으로 기록을 지우거나 새 아카이브 폴더를 만들지 않는다. 해결된 과거 상세를 줄이기 직전에, 해당 최신 항목이 지정한 커밋·당시 경로에서 실제로 복원되는지 확인한다. 예전 커밋 뒤에 덧붙인 미보존 내용은 남긴다.

TASK에는 버전 결과와 `커밋 ID + 당시 상대 경로 + 항목 제목/ID`의 짧은 조회 단서를 남긴다. 미해결·조사 중·사용 중인 우회와 현재 코드 이해에 필요한 주의사항은 현재 문서에 유지한다. 이력이 없거나 접근할 수 없으면 유일한 상세를 보존한다. 과거 조회는 관련 항목으로 범위를 좁히며 옛 원인·우회를 현재의 사실로 승격하지 않는다.

사용자 프로젝트 기록의 로컬 커밋 보존과 JOENESS 0.1 소스의 원격 보존 게이트는 별개다. 버전 정리 요청 자체는 commit·tag·push 권한을 추가하지 않는다. 별도 Git 아카이브 엔진은 만들지 않는다.

## 세팅과 운영 흐름

1. **읽기 전용 조사:** 정확한 프로젝트 root·branch·Git 상태, 상·하위 `AGENTS.md`, 기존 문서와 실제 코드·검증 명령을 확인한다. 모르는 목표·승인·자산·테스트 결과는 미확정으로 둔다.
2. **변경안:** 유지·재사용·생성·부분 수정할 실제 경로와 이유, 필요한 미확정 결정만 제시한다. 제품 구현이나 설치가 포함되지 않음을 분명히 한다.
3. **범위 확인:** 사용자가 승인한 프로젝트 문서 변경만 적용한다. `설명만`, `수정하지 마`, `기록하지 마`는 해당 요청 범위의 쓰기를 제한한다. 반론·취향·불만은 명시적 목표 변경으로 자동 승격하지 않는다.
4. **부분 적용:** 쓰기 직전에 대상의 최신 내용과 조사 스냅샷을 대조한다. AGENTS 소유 구역 밖의 바이트, 사용자 편집, 기존 지침을 보존한다. 각 대상은 적용 후 재읽어 확인한다. 변경이 없으면 쓰지 않는다.
5. **일상 운영:** 이후 일반 작업에서는 관련 문서만 읽는다. 승인된 업무의 실제 진행은 TASK, 중요한 문제의 상세는 ISSUES, 확정된 목표 변경은 ROADMAP, 승인 디자인 기준 변경은 DESIGN에 한 번만 기록한다. 질문만으로 문서를 수정하지 않는다.
6. **중단·재개:** 재개 시 오래된 TASK·인수인계보다 현재 파일·Git·대상 상태를 우선한다. 완료된 일을 반복하지 않고, 옛 계획으로 새 범위를 만들지 않는다.

여러 파일에 걸친 원자적 트랜잭션은 보장하지 않는다. 파일별 성공·실패를 구분하고, 예를 들어 제품 구현은 완료됐지만 TASK 기록에 실패했으면 두 결과를 별도로 보고한다. 동시 편집 충돌은 최신 내용을 다시 읽고 범위가 여전히 명확할 때만 재계획하며, 맹목적으로 재시도하지 않는다.

## 쓰기·해제 안전 계약

프로젝트 AGENTS의 새 소유 구역은 0.1의 `JOEWRKS-PROJECT` 구역과 다른 식별자를 사용한다. 보조 도구는 정확한 root·대상 hash를 받은 `-Check`/`-Apply` 경로로 **그 구역만** 생성·수정하고, marker 중복·손상·경로 재파스·root 변경·스냅샷 드리프트에서 멈춘다. 인코딩·줄바꿈·소유 구역 밖 바이트를 보존하고 적용 후 재읽는다. 0.1 구역이 기존 프로젝트에 있으면 자동 삭제하거나 조용히 새 구역을 중복 추가하지 않고, 변경안에서 전환 범위를 별도로 보여준다.

ROADMAP·TASK·ISSUES·DESIGN의 기존 사용자 내용 전체를 도구 소유로 취급하지 않는다. 에이전트는 현재 파일을 읽고 승인된 부분만 수정한다. 프로젝트 적용 해제는 AGENTS의 확인된 운영 연결만 대상으로 하고, 다른 지침과 과거 기록을 보존한다. 기록에 비밀값이나 거대한 로그 본문을 복사하지 않는다.

### C3 — 내부 편집 보존과 실제 해제 인터페이스

관리 marker는 변경 범위를 표시할 뿐 내부의 사용자 문장을 삭제할 권한이 아니다. 기존 0.1 helper의 `ExpectedTargetHash`는 Check 이후 변경만 검사하며, Check 이전의 내부 사용자 편집과 마지막 적용 본문을 구분하지 않는다. 따라서 이 코드를 그대로 가져오는 것으로 C3를 충족하지 못한다.

새 helper의 제안 인터페이스는 다음과 같다. 아직 구현된 명령은 아니다.

```text
project-setup.ps1 -Check -ProjectPath <root>
project-setup.ps1 -Apply -ProjectPath <root> -ExpectedRoot <resolved-root>
  -ExpectedTargetHash <sha256|absent> -ExpectedStateHash <sha256|absent>
  -ManagedBodyBase64 <utf8-body>
project-setup.ps1 -Detach -ProjectPath <root> -ExpectedRoot <resolved-root>
  -ExpectedTargetHash <sha256|absent> -ExpectedStateHash <sha256|absent>
```

적용 기준은 프로젝트의 `.joeness/setup-state.json` 한 파일에 둔다는 설계안으로 정한다. 내용은 schema/tool 버전, 대상 상대 경로 `AGENTS.md`, 마지막 적용 구역의 정확한 bytes와 hash, 도구가 삽입한 경계 bytes의 식별뿐이다. 업무 상태·대화·로그는 넣지 않는다. 이 메타데이터는 의미상 업무 `STATE.md`나 메모리 DB가 아니며 세팅/해제 때만 사용한다. 절대 사용자 경로는 저장하지 않고 실행 시 명시한 실제 root에 다시 결합한다. 해당 경로에 기존 다른 파일이 있으면 자동 인수하지 않는다.

구역 밖 편집은 현재 bytes를 그대로 보존한다. 현재 구역이 마지막 적용 기준과 다르면 `blockState=edited`로 반환하며 자동 교체·전체 해제는 하지 않는다. 에이전트는 사용자 내용을 보존하는 구체 변경안을 작성할 수 있지만 helper에 의미 추론·자동 3-way merge 기능을 넣지 않는다. 분리 불가능한 편집이나 근거 없는 구역은 정확한 충돌을 반환한다. marker와 상태 파일은 보안 권한의 증명이 아니다.

깨끗한 소유 구역의 Detach는 확인된 구역과 경계 bytes만 해제하며 AGENTS 파일 자체와 다른 프로젝트 문서는 보존한다. 이미 구역과 상태가 모두 없으면 무변경으로 성공한다. 한쪽만 없으면 중단된 적용/해제 가능성을 보고한다. 자동 기록만 중지할 때는 읽기 안내를 보존한 본문 갱신으로 처리하며 전체 Detach와 구분한다.

AGENTS와 상태 파일은 별도 쓰기이므로 원자적 성공을 주장하지 않는다. 쓰기 전 두 스냅샷을 확인하고 각각 재읽으며, 복구는 현재 bytes가 도구의 직전 쓰기 결과와 같을 때만 한다. 후속 사용자 편집이 있으면 보존하고 `partial`과 미해결 경로를 보고한다. 상태 파일에 마지막 적용 기록만 있다고 실제 AGENTS까지 성공했다고 보고하지 않는다.

## C4 — 사용자 안내와 확인 범위

README는 빠른 시작, 평소 요청, 기록 제한·교정, 재개·과거 조회, 기록 중지·프로젝트 해제·도구 제거, 문제 해결의 순서로 구성한다. 내부 문서 역할 표는 필요할 때 찾을 수 있게 둔다. 사용자에게 문서별 명령이나 매번의 기록 승인을 요구하지 않는다.

설치 옵션·스킬 호출·지침 재로딩 예시는 지원 런타임에서 확인한 결과만 배포 사실로 쓴다. 개발자의 안내 점검, 실제 에이전트 실행, 처음 쓰는 사람의 사용 확인은 각각 기록한다. 다른 에이전트가 README를 읽은 것을 사람의 사용자 수용으로 보고하지 않는다. 사용자 조사가 미실행이면 그 사실을 남기되, 별도로 요구되지 않은 매 작업 승인 절차를 추가하지 않는다.

## 검증과 릴리스 게이트

구현은 테스트 우선으로 진행한다. 기존 0.1 테스트의 역사적 결과를 지우지 않고, 0.2 검증은 별도 결과로 남긴다.

- **패키지 무결성:** 0.2 manifest가 얇은 Core와 `joeness-setup`만 활성화하는지, 파일 hash·진입점·README가 일치하는지 검사한다. 옛 활성 스킬과 vendor/runtime 의존성은 0이어야 한다.
- **설치/이관:** 빈 대상, 정상 0.1 설치 상태, 설치 파일 드리프트, 사용자 추가 파일, 불완전한 marker, 중도 실패를 fixture로 검증한다. 보존·백업·복구·재실행 무변경을 확인한다. 개인 설치본은 테스트 대상으로 직접 수정하지 않는다.
- **프로젝트 적용:** 기존 문서 재사용, 필요한 문서만 생성, 사용자 편집 보존, 같은 요청 재적용 무변경, 0.1 프로젝트 구역 충돌, 동시 편집·부분 실패를 fixture에서 확인한다.
- **행동 검증:** 최초 세팅 자연어/명시 호출, 일반 작업에서 비호출, 읽기 전용 질문, 기록 금지, 의견과 확정 결정 구분, stale 재개, 문제 재발, 디자인 승인 범위, 접근 불가, 중단·해제를 fresh context에서 확인한다. `이해했다`는 답변만으로 실제 읽기·쓰기 통과를 선언하지 않는다.
- **완료 보고:** 검증된 파일·상태만 완료로, 미실행 런타임 확인과 사용자 수용은 별도로 표시한다. 토큰 절감·품질 향상·OS 보안 강제 효과를 주장하지 않는다.

0.2 READY 조건은 승인된 Core 본문과 패키지 포인터의 일치, 원격의 제거 전 보존 확인, 현행 트리의 단일 활성 스킬, deterministic suite 통과, 설치/이관 fixture 통과, C1–C4의 구현/검증 연결과 fresh 동작 검증, 실제 지원 런타임 확인이다. 어느 필수 게이트든 실패하거나 미실행이면 READY를 선언하지 않는다. 설계 반영, deterministic 테스트, fresh 행동, 안내 점검, 런타임, 설치/이관, 사용자 수용의 상태를 하나의 PASS로 합치지 않는다.

## 구현 계획으로 넘길 파일 경계

세부 계획은 `docs/superpowers/plans/2026-09-26-joeness-0.2-project-setup.md`에 연결한다. 대상은 새 `skills/joeness-setup/**`, 0.2 공개 진입점·설치 스크립트, `vendor/source-manifest.json`, `README.md`, 해당 PowerShell/Node 테스트, 필요한 작은 fixture다. 기존 0.1 스킬·진입점 소스는 원격 보존을 확인한 뒤 현행 트리에서 제거한다. 루트 `AGENTS.md`, 승인된 얇은 Core의 문구, 과거 후보·실패 보고, 사용자 개인 설치와 실제 프로젝트 문서는 이 구현의 수정 대상이 아니다. 승인 본문의 새 패키지 소스 고정은 내용 확장과 구분한다.

이 명세와 연결 계획은 코드 구현·설치·삭제·commit·push·배포의 새 승인이 아니다. 이번 보완에서는 문서 두 개만 수정/작성하며 실제 기능은 미구현·미검증이다.

## 보완 제안 검토 판단과 남은 확인

C1과 C2는 통합 원문의 요구를 실제 실행 증거로 연결하므로 채택한다. C3는 실제 데이터 보존의 빈틈을 메우므로 우선 적용하되, 자동 병합 엔진 대신 작은 적용 기준과 충돌 반환으로 범위를 제한한다. C4는 채택하되 제안서의 긴 사용자 문구를 그대로 복제하지 않고 핵심 사용 흐름으로 줄인다. 제안서의 테스트 ID는 추적 단위이며, 고정된 테스트 수나 품질 보증 수치로 사용하지 않는다.

제안서는 현 저장소를 직접 검증하지 않았음을 밝히고 있으므로 그 문서의 인터페이스·설치·태그 주장을 실물 증거로 쓰지 않는다. 또한 제안서가 그대로 유지한 이전 설계의 Core 혼동은 위에서 정정했다.

자료 확인과 구현 검증으로 해결할 항목은 승인 Core의 패키지 bytes/hash, 지원 Codex 앱/CLI와 재로딩, 상태/파일 부분 쓰기 복구, 0.1 실제 설치 상태별 이관이다. 아직 결정되지 않은 지원 경계는 **Git 없는 폴더에서 최초 자동 세팅까지 제공할지**다. Git 없는 기록 조회·ZIP 인수인계의 비소실 동작은 포함하고, 이 결정 전까지 자동 Git 초기화나 non-Git 설치 지원을 광고하지 않는다. 사용자 안내의 사람 대상 확인은 미실행으로 유지한다.
