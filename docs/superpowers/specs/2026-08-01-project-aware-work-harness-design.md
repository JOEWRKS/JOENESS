# 프로젝트 인지형 작업 하네스 설계

**상태:** 사용자 승인, 구현 대상

## 목표

사용자가 프로젝트를 선언한 뒤 `해줘`, `계속해줘`처럼 넓고 짧게 요청해도 현재 저장소 증거를 기준으로 다음을 스스로 정렬한다.

1. 제품 결과와 실제 출시 목표
2. 현재 생명주기 단계와 다음 필수 산출물
3. 이번 작업의 권한·제약·완료 증거
4. 이미 끝난 일과 다음 작업 사이의 연속성

Codex 자체의 계획·도구·권한·검증 하네스를 다시 만들지 않는다. 이 하네스의 주목적은 거친 요청을 전문적인 실행 계약으로 번역하고, 실제 관찰된 이탈만 얇게 교정해 기획, 설계, 구현, 검증, 협업, 출시 준비가 끊기지 않게 하는 것이다. 과확장·중복·허위 완료 방지는 그 실행을 지키는 안전 속성이다.

## 구조

- **Common Core:** Codex 위에 별도 작업 체계를 얹지 않고, 모든 작업에서 요청을 현재 단계의 실행 계약으로 번역하며 현재 증거로 짧은 작업 나침반만 유지한다.
- **프로젝트 셋업 스킬:** 장기간 재사용할 프로젝트 목표·권한·명령·협업·출시 기준을 루트 `AGENTS.md` 관리 블록으로 영속화한다. 일반 프로젝트 선언과 `해줘`는 공통 코어가 처리하며, 셋업 스킬은 해당 프로젝트에 대한 명시적 설정·적용 요청에만 호출한다.
- **전문 스킬:** 현재 산출물에 독자적인 도움이 있을 때만 호출한다. 의미 있는 UI 작업은 기존 디자인/프론트엔드 스킬이 UI UX Pro Max, Apple Design, Figma, 브라우저를 조건부로 라우팅한다.
- **사실 원장:** 현재 Git, 파일, 테스트, 빌드와 실제 대상 상태다. 대화 기억과 handoff는 탐색 단서이지 완료 증거가 아니다.

새 범용 PM·백엔드·릴리스 스킬, 별도 메모리 서비스, 역할 의식, 자동 문서 세트, 프로젝트별 에이전트 팀·스킬 생성기는 만들지 않는다. 복잡한 작업만 프로젝트별 아키텍처·명세·테스트 기준을 점진적으로 읽고, 단순 작업에는 추가 스킬이나 에이전트를 붙이지 않는다.

## 실행 경계

넓은 자율 요청은 현재 단계에 필요한 가역적인 로컬 기획·설계·구현·검증을 계속 수행할 권한으로 해석한다. 제품 방향 변경, 삭제, 비용, 외부 쓰기, 게시·배포·스토어 제출, 이후의 선택적 단계까지 허가하는 것은 아니다.

요청 결과가 구현이나 출시 준비까지 포함하면 계획 또는 프로토타입만 만든 뒤 완료하지 않는다. 실제 결정이나 외부 권한 경계에서만 멈춘다. 출시 준비는 빌드 가능한 결과, 재현 가능한 명령, 검증 증거, 남은 외부 gate와 인수인계를 뜻하며 실제 출시를 뜻하지 않는다.

## 프로젝트 계약

영속 계약은 변동이 적고 검증된 내용만 담는다.

- 제품 결과, 대상 사용자·플랫폼, 출시 목표
- 비목표, 제약, 쓰기·외부 권한 경계
- 권위 있는 명세·디자인·상태 문서와 기술 스택
- 표준 실행·빌드·테스트 명령
- 계획→설계→구현→검증→출시 준비의 증거 기반 gate
- 유지보수·협업·릴리스 완료 기준과 남은 외부 결정

현재 상태 자체를 기억으로 고정하지 않고, 현재 저장소에서 재계산하며 기존 상태 문서가 있으면 그 위치만 계약에 연결한다.

## 최우선 실사용 합격 기준

하네스의 일차 효과는 일반 Codex 작업에서 반복되는 다음 실패를 줄이는 것이다. 전문 스킬 호출, 산출물의 추가 polish, 토큰 절감은 이 기준을 통과한 뒤 평가하는 이차 효과다.

- 현재 증거보다 강한 판단을 내리거나, 확인하지 않은 상태를 사실로 전제하지 않는다.
- 요청한 현재 단계보다 앞선 기능·문서·추상화·의존성을 필요성 증거 없이 구현하지 않는다.
- 프로젝트 목표·현재 단계·기존 흐름·근본 원인과 어긋난 경로를 선택하지 않는다.
- 하지 않은 구현·수정·검증·실행을 했다고 보고하거나, 부분 완료를 전체 완료라고 부르지 않는다.
- 같은 입력·가설·관찰 방법으로 진전 없는 행동을 반복하거나, 앞선 결론을 새 근거 없이 뒤집으며 순환하지 않는다.

실사용 검증에서는 각 실패의 발생 여부, 심각도, 발견까지 걸린 시간과 재작업량을 일반 Codex와 비교한다. 추가 기능이나 보기 좋은 산출물이 위 실패를 상쇄하지 않으며, 토큰 절감도 필요한 증거 확인을 생략한 결과라면 개선으로 인정하지 않는다.

## 비교

동일한 빈 Git 프로젝트에서 instruction-free Control과 후보 Core를 각각 새 대화 세 번으로 이어 간다.

1. 프로젝트 선언과 `해줘`
2. 과거 대화 없이 `계속해줘`
3. 과거 대화 없이 `출시 직전까지 준비해줘`; 외부 게시·배포 금지

먼저 최우선 실사용 합격 기준의 실패 발생 여부·심각도·재작업량을 비교한다. 그 뒤 실행 가능 결과, 단계 전진과 중복 방지, 유지보수·협업 가능성, 로컬 출시 준비, 전문 스킬의 고유 기여, 토큰과 시간을 비교한다. 실제 스토어 출시·운영·장기 조직 협업은 이 평가로 증명하지 않는다. 한 번의 표본은 방향성 증거이며 승격 확정 근거가 아니다.
