# Project working connection

Adapt this body to actual existing paths before applying; omit unused roles.
- Purpose: file facts by role so successors recover purpose, progress, problems
  and next action.
- Sources: product <canonical path>; current work <task path>; issues <issue path>;
  design <design path, if relevant>; direction <roadmap path, if relevant>.
- On resume use current files/Git/target state; old notes locate sources, not new
  scope. Do not repeat work that is already complete. If inspection finds no changed
  task fact, report its completed status without a repeat verification note.
- Recording consent: <agreed scope>. After authorized work, record material facts
  in the task source; reusable causes/fixes/workarounds in issues. Avoid duplicate
  prose. Questions, opinions, explanation-only and no-record requests cause no
  record writes; no-record does not cancel separately authorized implementation.
- After substantive work, lead with six terse, plain-language hyphen bullets in the
  user's language: 작업, 업데이트 파일, 이슈, 해결, 남은 문제, 다음 작업 (translate labels if needed).
  Use fragments, not paragraphs, acronyms, internal requirement IDs or milestone
  codes in these six lines; use a plain task name instead. Name only files actually
  changed; use 없음 for empty fields. 이슈 is a problem found; 해결 is only a verified
  correction; 남은 문제 is what remains unresolved or unverified. Do not call an
  unresolved issue solved or invent a remaining problem.
  Derive the next task from approved scope/roadmap, never invent it. Put material
  proof, recording details, IDs or paths under 상세 보고 only if useful or asked.
  For a human handoff asking for cause, verification, scope, acceptance or stale
  records, keep the six bullets short and put the exact facts and source pointers
  under 상세 보고; do not omit them to make the opening shorter.
  Keep required verification gaps and user acceptance distinct. Use checked
  facts, with no extra formatting pass or claimed write without a write.
- Only explicit direction changes update roadmap. Preserve product/design authority;
  proposed changes, observed verification, and user acceptance are distinct.
- Update an approved required roadmap item's check/evidence state from actual
  verification; this is not permission to change its scope or priority.
- A finished task does not finish its milestone or release. Use the approved
  roadmap's required-item checks and evidence for that completion claim;
  scope changes or deferrals need an explicit authorized decision.
- For a requested human handoff, use the same six-field opening, followed by
  only needed detail. Keep technical completion and user acceptance distinct.
  Simple questions need no work receipt.
- If a source/write is unavailable, report the exact boundary and continue independent
  authorized work. Never pretend a failed record was saved.
- Historical detail: follow recorded exact Git commit:path references when needed.
  Keep latest unarchived detail, active issues and effective workarounds visible.
