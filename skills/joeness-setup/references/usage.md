# JOENESS 0.3 사용 안내

설치하면 두 가지가 준비됩니다. 하나는 답변할 때 근거를 다시 따지게 하는
공통 지침이고, 다른 하나는 프로젝트 문서의 위치를 연결하는
`joeness-setup` 도구입니다. 프로젝트 문서 5개는 설치만으로 자동 생성하지
않습니다.

JOENESS는 보이지 않는 곳에서 계속 일하는 프로그램이 아닙니다. 프로젝트를
정리해 달라고 하면 기존 문서를 살펴보고 연결할 내용을 제안합니다. 사용자가
적용을 승인하면 그때 설정 파일을 바꿉니다. 평소 작업 기록도 동의한 범위에서
실제 작업을 할 때만 남깁니다.

핵심은 보고서 모양이 아니라 **프로젝트 사실을 맞는 문서에 남겨** 다음 담당자가
목적·진행 상황·문제·다음 일을 찾을 수 있게 하는 것입니다.

## 처음 사용하기

1. 작업할 프로젝트를 Codex에서 열고 새 세션을 시작합니다.
2. `$joeness-setup으로 이 프로젝트 설정안을 보여줘.`라고 요청합니다.
3. 연결할 기존 문서, 필요한 새 문서, 기록 범위를 확인한 뒤
   `이대로 적용하고, 작업 결과와 문제 해결 내용을 기록해줘.`라고 승인합니다.

## 문서 5개의 역할

아래 이름은 역할별 기본 예시입니다. 기존 문서가 있으면 이름과 경로를 그대로
사용하고, 필요한 역할에 문서가 없을 때만 생성안을 제안합니다.

| 문서 | 역할 | 언제 사용하는가 |
|---|---|---|
| AGENTS.md | 작업 규칙, 원본 문서 위치, 동의한 기록 범위를 연결하는 안내판 | 작업 시작·재개 때 에이전트가 참고 |
| ROADMAP.md | 목표·구현 순서, 현재 단계, 필수 항목의 상태·완료 기준 | 작업을 시작·재개하거나 단계 완료를 판단할 때; Product 원본을 대체하지 않음 |
| TASK.md | 현재 승인된 작업 범위·진행·실제 검증 결과·남은 일 | 진행 상황 확인과 이어서 작업할 때 |
| ISSUES.md | 문제 증상·확인된 원인·해결·검증·유효한 우회책 | 같은 문제가 재발하거나 과거 해결책을 찾을 때 |
| DESIGN.md | 디자인 원본과 승인 사항의 연결 | 디자인 관련 작업이 있을 때; 제안·검증·사용자 승인은 구분 |

`PRODUCT.md`는 이 기본 다섯 문서에 포함되지 않습니다. 프로젝트에 이미
제품 기준 문서가 있다면 그 실제 이름과 위치를 연결할 수 있지만, JOENESS가
새로 설치하는 문서는 아닙니다.

작업을 시작하거나 이어받을 때 ROADMAP에 정해진 현재 단계와 필수 항목을 먼저
확인합니다. `미완·작업 중·검증 대기·보류`는 남은 일이고, `완료`는 실제 확인을
마친 일입니다. 구현만 끝나고 현장 확인이 남았다면 `검증 대기`입니다.
TASK에는 개별 작업의 결과를 남기되, 필수 항목이 모두 확인되기 전에는 단계를
완료라고 하지 않습니다. `범위 제외`는 삭제나 완료가 아니라 사용자 등 권한 있는
사람의 결정과 이유를 남기는 상태입니다. 선택 항목은 자동으로 완료를 막지
않습니다. 이전 단계에 의존하지 않는 승인된 작업은 계속할 수 있습니다.

설정이 끝나면 실제 연결·생성·수정한 경로와 각 역할, 사용하지 않은 역할을
알려줍니다. 원래 문서와 새로 만든 문서는 구분하며, 디자인 작업이 없으면
DESIGN.md를 억지로 만들지 않습니다.

실제 작업 뒤에는 먼저 짧은 여섯 줄 보고체로 알립니다. 첫 여섯 줄과 뒤의
상세 보고 모두 비전공자도 이해할 자연어로 씁니다. 긴 문장이나 설명 없는
약어·내부 작업 번호 대신 사용자가 아는 작업 이름으로 말합니다.
예를 들어 오류는 고쳤지만 현장 확인이 남았다면:

- 작업: 예약할 때 이름이 빠지고 취소하면 기록이 사라지던 오류를 고침.
- 업데이트 파일: 예약 기능, 자동 검사, 작업·문제 기록.
- 이슈: 이전 검사는 두 오류를 찾아내지 못했음.
- 해결: 기능을 고치고 새 검사를 모두 통과함.
- 남은 문제: 실제 행사장 기기에서는 아직 확인하지 못해 전체 완료 전.
- 다음 작업: 행사장 기기에서 예약과 취소를 확인하고 결과를 기록.

상세 보고도 짧게 씁니다. 예: “예약을 만들 때 이름을 빠뜨렸고, 취소할 때
기록을 지웠습니다. 예약 기능(`src/slots.mjs`)을 고친 뒤 자동 검사 6개를
모두 통과했습니다(`tests/slots.test.mjs`). 현장 기기 검증과 사용자 수락은
아직 없습니다.” 쉬운 말은 긴 풀이가 아니라 익숙한 단어 선택입니다.

`이슈`는 작업 중 발견·확인한 문제, `해결`은 실제로 고쳐 검증한 내용,
`남은 문제`는 작업 뒤에도 미해결이거나 검증되지 않은 부분입니다. 없으면
`남은 문제: 없음`이라고 씁니다. 문제 원인, 검사 결과, 정확한 파일 위치 등
필요한 근거는 그 아래 `상세 보고`에 둡니다. 상세 보고에서도 쉬운 단어와
짧은 문장을 쓰고, 필요한 정확한 이름과 수치를 해당 사실 옆에 적습니다.
실제로 바꾼 파일만 적고, 문제가 없으면
`이슈: 없음`이라고 씁니다. 해결하지 못한 일을 해결했다고 쓰거나 계획에 없는
다음 일을 만들어 내지 않습니다. 인계에서 원인·검증·승인 범위나 오래된 기록을
물었다면, 여섯 줄을 늘리는 대신 그 정확한 사실과 출처를 `상세 보고`에 남깁니다.
보고를 위해 파일을 다시 읽거나 검사를 한 번 더 돌리지 않습니다. 질문만
받은 경우에는 이 형식을 강제하지 않습니다.

## 설정 후에는 평소처럼 요청하기

- 작업: `로그인 오류 고쳐줘.`
- 재개·현황: `어디까지 했는지 알려주고, 남은 작업을 이어서 진행해.`
- 새 담당자 인계: `처음 보는 사람도 알 수 있게 끝난 일·남은 일·다음 행동부터 알려줘.`
- 과거 해결 조회: `이전에 이 오류를 어떻게 해결했는지 찾아봐.`
- 이번 작업 기록 제외: `코드는 고치되 이번 작업은 문서에 기록하지 마.`
- 지속적인 기록 중지: `자동 기록만 중지하고, 문서 위치 연결은 남겨줘.`
- 프로젝트 해제: `이 프로젝트에서 JOENESS 연결을 해제해줘.`

매 작업마다 setup을 다시 호출할 필요는 없습니다. 에이전트가 작업하면서
동의한 범위의 사실을 기록하는 것이며, 별도 백그라운드 기록기는 없습니다.
질문·의견만으로 문서를 갱신하지 않습니다. 기록 중지, 프로젝트 연결 해제,
패키지 제거는 서로 다릅니다. 연결을 해제해도 일반 프로젝트 문서는 남습니다.
인계 답변도 위 여섯 항목을 먼저 쓰고, 작업 번호와 검증 근거는 뒤에 둡니다.
