# DungeonGameV3 지침 분리·새 채팅 검증

후속 판정 경계(2026-10-04): 아래 새 채팅 결과는 당시 현재 문서를 찾고 상태를 추출한 증거다. 이후 실제 운영 T500이 기존 T478 근거를 놓쳐 중복 작업을 선정했고 본 검토도 놓쳤다. 따라서 문서에 적힌 ‘다음 작업’을 읽은 성공을, 그 계획의 사실 정확성이나 기존 근거 탐색 성공으로 확대하지 않는다. [운영 실패·정정](../2026-10-04-roadmap-operation/review-evidence.md). 연결·원문 보존·읽기 전용 검사 결과는 이 발견과 구분해 유지한다.

현재 상태: **보완 및 영향 범위 재검증 완료(한 사례)**. 공식 연결 갱신 성공, 새 채팅 판단 유지 및 전체 출력/잘림 해소. 과거 잠금의 근본 원인과 일반적인 토큰 절감은 미입증. 아래 최초 부분 실패는 보존하며 최신 결과는 마지막 보완 절을 따른다. 게임 개발·제품 기준 변경·개인 설치·배포·commit/push 제외.

대상: `D:/JOEWRKS/.worktrees/T081-runtime-pass1`. 기존 담당자 `01a084de-a56e-77d1-a123-4ac5f4d06b84`가 원문 보존 및 역할별 정리를 수행한다. 저장된 앱 프로젝트 `927516c6-e74e-4b90-a45d-0e7fc80d9564`의 경로가 같은 작업본임을 확인했다.

기준 AGENTS: 39,918 bytes, SHA-256 `c6f38ea0b95e28825a6ef2d72e2aa46762ba349b4dc1dd541b665edf22d3571c`. 적용 후보 SKILL: `72c0d978cade38f22cd834102988ffc3cd2ee873bca5a8701c18fa1bbea682d4` (0.3.1-dev). 후보와 개인 설치를 바꾸지 않는다.

## 검사 범위

1. 원문 복원 가능성, 현행 제약/미해결 사항 유지 및 절별 새 위치 매핑.
2. 상시 핵심·조건부 상세·과거 이력 구분. 모든 참조 문서를 상시 읽도록 옮기는 방식 금지.
3. 공식 연결 도구 Check/Apply/Check 및 실제 AGENTS/문서 내용 확인.
4. 같은 저장된 프로젝트에서 새 로컬 채팅 1개 생성. 예상 답이나 파일 경로를 알려주지 않는 읽기 전용 인수인계 요청으로 현재 단계·남은 조건·다음 작업·완료 경계 조회 확인.
5. 전달된 규칙에 따른 행동과 읽은 문서 경로로 판정. 앱 내부 초기 프롬프트 bytes의 직접 입증과 구분. 게임 실제 동작·토큰/성능 우월성으로 확대하지 않는다.

새 채팅 답변을 보기 전에 기대 경계를 고정한다: 문서 정리와 제품 완료는 별개. 현재 제품 위치는 ROADMAP 최신 근거로 판단하고, 미실시 휴대폰/청취/사용자 관찰/최종 승인 및 부분 구현 조건을 유지해야 한다. 기존 증거의 공백 특정이 다음 독립 작업이며, 반복 검사나 게임 완료 주장을 하면 실패다. 실행 시 현재 원본이 정당하게 달라졌다면 그 근거를 우선 확인한다.

## 정리 및 보존 결과

- AGENTS: 39,918 → 9,231 bytes(약 77% 감소), 최종 SHA-256 `b4a95a4d07db3438a09b65a704d175ef98f6bff373eb1232cb3677ea8bb3e744`.
- 핵심 권한·저장 보호·제품 제약·단계 완료 경계는 상시 유지. 상세 17절은 DEVELOPMENT_RULES(신규), PROJECT_OPERATING_CONTRACT, SOL_VISUAL_QA_PROTOCOL, TICKET_EXECUTION_REPORT_TEMPLATE에 보존. 기존 상세 정본·과거 TASKS는 조건부 참조. 현행 규칙을 과거로 격하하지 않음.
- 원문은 대상 프로젝트 `.joeness/backups/t498/agents-before.txt`에 동일 SHA로 보존. 절별 매핑과 적용 실패는 해당 프로젝트 TASKS의 T498에 기록. 본 에이전트가 별도로 원문 17절과 이관 본문을 제목 깊이/EOL만 정규화하여 대조, 모두 일치 확인.
- 담당자 검증: 보호 대상 270개 및 외부 후보/개인 스킬/분석 보고서 11개 해시 동일, 기존 TASKS 본문·HEAD·index 보존. 본 에이전트도 최종 문서 diff check와 후보 SKILL 해시 불변 확인. 전체 게임 검사는 문서 정리의 증거로 재실행하지 않음.

## 실패 및 미해결

1. 공식 Apply 2회 모두 `File.Replace: The process cannot access the file because it is being used by another process.`로 실패. 원복 완료, changedTargets/unresolvedTargets 없음. 기존 관리 블록·상태는 유지되고 최종 Check는 current/clean. **새 관리 연결 적용 성공과 다름.** 사후 두 대상의 배타적 읽기 열기는 가능했으나 실패 순간의 잠금 주체·원인은 미확인. 강제 해제·프로세스 종료·수동 상태 수정·추가 무근거 재시도 없음.
2. 기존 보고 템플릿의 첫 줄 상태 표기와 관리 블록의 여섯 항목 시작 규칙 충돌은 T498에 보존. 이번 파일 분리로 임의 계약 변경하지 않음.
3. 새 채팅은 올바른 문서를 선택했으나 넓은 역사 검색(원출력 323,277자), 로드맵 후반/체크리스트 전체 출력(112,208자)으로 잘림 후 좁혀 재조회. 다른 상세 규칙을 전부 읽지는 않았지만 **읽기 효율 통과로 판정하지 않음**. 이는 도구 원출력 길이이며 실제 입력 토큰 계측이 아님.

## 사용자 `보완` 승인 후 결과

- [사전 기준·해시·동일 질문](correction-plan.json), [결과·명령·전후 해시](correction-results.json), [새 채팅 답변](correction-response.md). 새 채팅 `01a106b8-7d02-77c3-ae38-3eab77132a58`에서 한 번 재검증 후 종료.
- 파일 잠금: 공식 helper 코드를 읽고 열린 스트림 보유 여부를 검토. Windows Restart Manager의 읽기 전용 조회에서 두 대상의 점유 프로세스는 없었음. fresh Check 후 공식 Apply `current/clean`, changedTargets는 AGENTS와 setup-state뿐. 관리 블록 밖 동일 확인, 후속 Check 통과. 실패 순간 원인을 특정한 것은 아니므로 기존 두 실패를 근본 원인 해결로 소급하지 않는다. 별도 프로세스 종료/도구 설치/안전 절차 우회 없음.
- 내용: 후보의 승인된 lookup/dependency/completion/status-update 연결 적용. 사용자 소유 AGENTS에는 제한 검색→필요 구간 읽기→미답 질문만 확대하는 문장 하나 추가. 체크리스트에 현재 요약과 후속 이력의 경계 제목만 추가. 보고 템플릿은 사용자에게 보내는 여섯 항목 뒤 필요한 상태를 표기하도록 정합화했으며 PM 승인권/티켓 필드 불변. 상시 AGENTS 최종10,384바이트(최초39,918 대비 약74% 축소). JOENESS 스킬/도구 소스 수정 없음.
- 보존: 이전 TASKS는 새 T499 항목을 제거해 계산한 SHA가 원본과 일치. 체크리스트는 추가 제목 제거 및 patch가 바꾼 한 줄 LF를 원래 CRLF로 대조하면 원본 SHA와 일치. ROADMAP 원본 해시 유지, 기존 요구 행/제품 검증 상태 불변. 문서 diff check 통과.
- 행동: 같은 인수인계 질문에서 현재6단계+이전 열린 조건,7단계 미실행,4/15/2 요구 상태,기존 근거의 공백 조사와 단계/제품 완료를 분리. 파일 쓰기/게임/새 검증/기기 작업 없음. 조회4회,11개 파일 해시 전후 동일.
- 출력량: 이전4개 원출력 합475,762자→이번44,490자(약91% 감소). read_thread의 발췌 상한16,000자로 첫 출력이 표시상 잘린 것을 전체17,242자를 포함하는20,000자 조회로 다시 확인; 실제 이번4개 명령 출력은 잘림 없음. 원출력 글자 수이지 실제 모델 토큰 사용량이 아니며 제어된 성능 A/B도 아니다.
- 남은 한계: 일부 과거 근거를 요약 종료선보다 더 읽었으므로 ‘최소 조회만 수행’은 미입증. 여섯 항목의 ‘이슈’에 실제 오류 대신 미커밋 주의를 쓴 표현 품질도 남음. 이 한 사례의 정확성/출력량 개선을 일반 성공률로 확대하지 않는다. 관련 없는 추가 규칙·반복 시험은 추가하지 않는다.
- 작업 중 검사 한계: 첫 진단 명령은 PowerShell foreach 파이프 구문 오류로 실행 전 실패해 문법 수정 후 조회. 첫 사전 bytes 수집은 큰 TASKS가 응답 상한을 넘어 parse 실패하여 디스크 수정 없이 경로별 해시 수집으로 전환. 최종 보존 판정은 위 독립 해시 검사 사용. 첫 복수파일 patch는 일치하지 않는 행으로 실패해 실제 상태 확인 후 정확한 줄로 적용. 원인·실패를 성공 근거로 대체하지 않음.

이 보완의 연결·읽기 검증 항목은 종료한다. 잠금이 재발하면 그때의 점유/실패 조건을 조사한다. 게임 다음 작업 및 JOENESS 배포는 각 로드맵의 별도 범위로 남는다.
