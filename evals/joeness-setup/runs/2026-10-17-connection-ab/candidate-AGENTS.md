# Project working connection

- Owners: AGENTS = work rules and source locations; ROADMAP = delivery goals,
  order, required outcomes/checks, current state and next work; TASK = execution
  and verification; ISSUES = unresolved defects/workarounds and closure evidence;
  DESIGN = visual rules/approval; Library = topic knowledge. Product: PRODUCT.md.
- Start at the current roadmap item and relevant records/target, not all history.
  Approved owners govern intent; current targets/proof govern facts. Neither a
  newer note nor working code grants approval. Old handoffs are locators, not scope.
- Check entry conditions before dependent work; continue independent authorized
  work. Change scope/order/criteria only by authorized direction. Before declaring
  completion, compare required outcomes with actual proof; keep missing checks,
  unresolved risks and required acceptance open. A finished task is not its stage.
- Recording consent: code, tests and factual TASK/ISSUES/ROADMAP updates within the
  requested task. Store detail once in its owner, concise links/state elsewhere.
  Before handoff, update affected state/gap/next; keep former next-work notes as
  history. Preserve cause, evidence, uncertainty and approval boundaries. No extra
  report file or rewrite pass; no change means no repeat record.
- Required external verdict: none. Do not invent checker/receipt requirements.
  If explicitly connected for a scope, missing/failed/stale results keep that
  verdict pending. Keep implementation, technical, visual and acceptance separate.
  Reuse applicable proof; rerun for a named change, failure or uncovered condition.
  Inspect linked proof before declaring it absent. Report read/write gaps without
  abandoning independent work. Questions/no-record requests cause no record writes.
- Credential handling, concurrent shared-record edits or requested history cleanup:
  read `.joeness/connection-details.md` for that operation; do not load it routinely.
- After substantive work/handoff, report six short everyday-language bullets:
  작업, 업데이트 파일, 이슈, 해결, 남은 문제, 다음 작업. Use 없음 when empty.
  Report actual changes; 해결 means a verified fix, not a passing test. Put necessary
  evidence/limits after the summary without repetition. Simple questions need no
  work report. Next work must come from authorized scope or the roadmap.
