# 규칙 생성·누적 실험 독립 검토

검토 대상: 2026-10-17-rule-accumulation. 부모의 해석·결론은 받지 않고 지정된 원자료를 읽었다. 제품·개인 설치·시험 코드 변경, 네트워크, 새 시험 실행 없이 이 파일만 작성했다.

## 판단

이 네 경로에서는 **누적된 지침 때문에 새 담당자가 허용된 해법 변경을 거부하거나 추가 승인을 기다린 사례를 확인하지 못했다.** S4 네 구현 모두 이전 입력 방식을 실제 코드에서 바꿨다. 두 게임은 도구·횟수 중심 조작을 개별 물체 조작으로 바꾸었고, 두 메모는 분류 없이 여러 줄을 저장하고 내용으로 찾아 개별 수정하는 경로와 일반 글 파일 입력을 만들었다. 기존 취소·재시작·저장 보존 검사는 새 입력 방식에 맞춰 유지하거나 이식했다. 이는 구현 변화에 관한 결과이며, 직관성·재미·현장 유용성이 개선됐다는 사용자 증거는 아니다.

그렇다고 불필요한 규칙 생성 우려가 사라지는 것은 아니다. A 게임에는 “최종 인계 전 실제 브라우저” 확인, A 메모에는 “다음 수정 전에” 실제 브라우저·사용자 관찰이라는 선행 의무 표현이 생겼다. J 두 경로에서는 실제 브라우저 관찰을 ROADMAP의 필수 결과와 단계 완료 조건으로 올리고, 이후에도 미검증 단계·현재 다음 작업으로 유지했다. **관찰 공백을 정직하게 남기는 목적과, 선택적 검증을 모든 후속 작업의 선행 조건으로 만드는 것은 구분해야 한다.** 이 실험에서 관찰된 J의 효과는 완료 상태와 다음 작업의 지속적 구조화이며, 구현 차단까지는 아니다.

JOENESS는 필수 결과·근거·완료 조건을 기록하는 틀을 직접 제공했다. 그러나 “이 시제품은 반드시 실제 브라우저 확인을 마쳐야 단계 완료”라는 구체적 기준, 펌프·집게·JSON·분류·글자 수·파일 구조는 작업자가 선택했다. 그 선택의 형식적 승격에는 JOENESS가 기여했을 가능성이 있으나, A에서도 비슷한 의무 문구가 발생했고 제거 반사실 실험이 없으므로 발생 원인과 후속 효과를 단정할 수 없다.

## 읽은 범위와 증거 표기

- `plan.md`, `protocol-notes.md` 전체, `fixtures.json`의 네 실제 요청·전체 프롬프트·초기 BRIEF/파일, `document-history.md` 1–1396행 전체를 읽었다. 문서 이력은 새 문서 전문과 후속 줄별 diff다.
- `gN-stageM.json`의 문서 원문을 필요한 맥락에서 대조하고, S4 네 경로의 핵심 모델·앱 연결·HTML 및 관련 검사 본문을 직접 읽었다. 게임 g1의 시각 단서 CSS도 대조했다. 아래의 `g2 S3 README:41`은 `g2-stage3.json` 안 `files["README.md"].text`의 41행을 뜻한다. 행 번호는 JSON 파일 자체의 물리적 행 번호가 아니다.
- `E(g2,S3)`는 `execution.json`의 `/root/growth_g2`, 세 번째 turn이다. S4는 `/root/growth_resume_g2`의 첫 turn이다. 명령·종료 코드·쓰기 경로·최종 보고만 사용했고 내부 추론 기록은 읽지 않았다. 이 파일의 쓰기 목록은 턴별 집계이므로 코드와 검사의 정확한 편집 순서를 그것만으로 복원하지 않았다.
- `F(g2)`는 `final-audit.json`의 해당 run이다. 부모가 보존한 재실행 결과이며 독립 검토자가 재실행한 결과로 표현하지 않는다. 네 run의 `stage4SnapshotMatches`와 모든 단계 BRIEF 보존은 true, 최종 test exit는 모두 0이다. tests/pass는 g1 57/57, g2 45/45, g3 45/45, g4 42/42이며 구문 검사도 exit 0이다. 검사 수는 품질·창의성 점수로 사용하지 않았다.
- 패키지 비교는 격리 `package/SKILL.md`, `assets/AGENTS.md`, ROADMAP/TASK/ISSUES/DESIGN 템플릿을 읽었다. 실제 지침으로 새로 적용하지 않았다. 원본·설치본·복사 패키지의 보존은 `final-audit.json.checks`의 expected/actual 일치 기록에 의존한다. source에는 17개 payload와 manifest, personal에는 payload와 state가 포함된다.

출처 표기: **U** = 사용자/환경의 명시된 경계·목표. **J-L** = JOENESS의 직접 지시를 번역·경로 적응한 것. **J-D** = JOENESS 틀을 적용해 작업자가 구체화한 파생 규칙. **W** = 작업자의 제품·구현·검사 선택. **A?** = 여러 출처가 겹쳐 정확한 생성 원인을 분리할 수 없음. W는 곧 잘못이라는 뜻이 아니다. 위임받은 설계·안전 선택은 정당할 수 있다.

## 좁은 실패 예방이 일반 제약으로 커졌는가

확인된 범위 확장은 두 종류다. 입력 취소·늦은 이벤트 방지는 장면 전환과 새 물체 입력으로, 저장 실패 원문 보존은 백업 및 일반 글 묶음으로 확장됐다. 이들은 같은 실패 기전과 사용자 보존 목표를 공유한다. 기존 기록을 분해하지 않거나 JSON 실패를 일반 글로 삼지 않는 검사도 정당한 데이터 보존이다. 이 확장을 “규칙 수 증가”만으로 과규제로 판정하면 실제 목표를 놓친다.

반면 g1의 “최종 인계 전”과 g4의 “다음 수정 전에”는 특정 관찰 공백을 후속 작업 전반의 순서로 넓힌 표현이다. 이 부분은 불필요한 선행 의무 후보를 넘어 문언상 확대가 분명하다. 다만 이후 작업자가 그대로 실행하지 않았으므로 이 실험은 그 규칙의 **존재**와 **비집행/완화**를 보여 주며, 비용·지연·해법 억제를 보여 주지는 않는다.

J의 R4/P2는 더 미묘하다. 실제 화면을 확인하지 않고 실제 화면이 검증됐다고 하지 않는 것은 옳다. 그러나 선택적 관찰을 “필수 결과”와 완료 조건에 넣은 것은 사실 기록만이 아니라 기준 선택이다. JOENESS의 필수 결과/상태 체계가 이를 오래 유지하게 한 경로는 보인다. S4까지 현재 단계가 계속 미검증이고 다음 작업이 실제 관찰로 남아 있는 것이 그 효과다. 다만 SKILL은 작업과 단계 완료를 구분하며 독립 작업을 허용한다. 실제로 모든 후속 요청이 실행됐으므로 **표현상 단계 완료의 강화**와 **승인된 구현의 차단**을 합쳐 결론내릴 수 없다.

g3 P6처럼 구체적 해법이 “필수 결과”에 섞인 사례도 있다. 해법을 고정할 잠재 경로이지만 S4는 그 항목 자체를 새 요청에 맞게 바꿨다. g1도 공통 engine의 집게 해법을 바꾸고 복사 금지 문구를 제거했으며, g2/g4는 정형 저장 계약과 분류 UI를 분리했다. “과거의 코드나 시험을 지키느라 새 해법을 못 만든다”는 가설에는 이 네 S4가 반대근거다.

## 귀속을 제한하는 원문과 반대근거

1. **패키지 원문에 상충 방지 문구가 실제로 있다.** SKILL:23은 “handoffs locate sources, not new scope”, :116은 “do not turn every implementation step into a gate”, :192–203은 독립적으로 승인된 작업의 계속 진행을 허용한다. assets/AGENTS는 외부 필수 게이트가 none이면 “do not invent a missing checker or receipt requirement”라고 명시한다. 따라서 브라우저/펌프/JSON 조건을 JOENESS의 직접 명령이라고 인용하면 잘못이다. 다만 이 문구가 모든 작업자 파생 기준을 방지했다는 결론도 아니다.
2. **J에만 발생한 구조는 있다.** 두 J 경로가 canonical 문서, 필수 ID, 단계 미완료와 같은 현재 다음 작업을 유지한 것은 treatment와 추적 가능한 연결이 있다. 둘 다 모든 후속 작업을 수행했다는 사실은 차단 가설에 반대되지만, 기준 승격·장기 누적 가능성을 없애지는 않는다. 실제 패키지와 초기 승인 매핑을 묶은 효과이며 그중 어느 문장 때문인지는 분리되지 않는다.
3. **A에도 강한 규칙이 생겼다.** g1 S2 README:32와 g4 S1 WORKLOG:31은 패키지 연결 없이 생긴 선행 의무 표현이다. test-first·특정 파일·보존/백업 규칙도 A에 존재한다. 이는 보통 작업자에게도 이런 경향이 있음을 보여 주지만 J가 이를 증폭시키지 않는다는 인과적 무혐의 증명은 아니다.
4. **실제 승인 행동과 제품 UI 확인을 혼동하면 안 된다.** 삭제·초안 폐기·파일 가져오기 확인은 데이터 조작의 UI 설계다. 네 S4 작업자가 구현 승인을 다시 요청한 것은 아니다. TXT에 확인이 남았어도 일반 붙여넣기에는 추가 승인 단계가 없고 A/J 모두 코드에서 확인된다.
5. **정당한 미검증 상태를 벌점으로 처리하지 않았다.** g3의 발견성, g2의 실제 브라우저 저장, 모든 경로의 사용자 유용성은 실측이 없다. 테스트 통과만으로 이들을 완료 처리하지 않은 것은 사실 정확성이다. 우려 지점은 관찰 공백을 어떤 범위의 선행 조건으로 만들었는지다.

## 실험의 한계

- 표본은 두 제품·각 두 조건의 네 경로이며 S1–S3와 S4를 독립적인 반복 표본으로 세면 안 된다. 중간 구현과 작업 난도도 다르다. g4는 백업을 S1에 먼저 구현했고 g2는 S3에 처음 구현했다. g1은 부분 진행을 계속 쌓고 g3는 짧은 미완료 조작을 취소하는 등 초기 상태 의미도 달랐다.
- A는 무지침 모델이 아니다. `execution.json`의 여덟 context 모두 동일한 root-instruction SHA-256 `ca99f59181fe14b179dafaffc39278ab9452f6427d560f6ea61cb6c1e2a68ee8`를 받았고 JOENESS 저장소 경계와 이전 Bare/Core 동등 결과 문구도 포함됐다. 일반 developer 지침도 공통이다. 공유된 priming과 환경은 외적 타당도를 제한한다. 동등 해시는 영향을 제거한 증거가 아니다.
- 같은 `gpt-6-astra / xhigh` 실행이 E의 16 turn_context에서 확인되지만 모델 변동성과 초기 선택의 영향은 남는다. g3 S1의 일본어 금지문 일부는 즉시 같은 의미의 한국어로 정정됐으며 재시작하지 않았다는 protocol 편차도 남는다.
- S2/S3 요청이 명시적으로 “작업 방법” 기록을 요구했다. 따라서 지침 누적은 처리와 과제 자체 양쪽에서 유도된다. J에 대한 기대나 부모 결론은 검토자에게 제공되지 않았지만 패키지/조건 표시는 읽어야 했으므로 완전 맹검은 아니다.
- E에는 최종 보고·명령·쓰기 경로가 있으나 내적 동기나 모든 편집 순서의 근거는 없다. 문서를 읽고 검사한 뒤 변경했다는 시간적 연관만으로 특정 규칙이 선택을 유발했다고 단정하지 않았다. 실행 로그에 없는 장기 지연/중간 승인 의도를 추정하지 않았다.
- 브라우저 렌더·실물 터치·클립보드·사용자 관찰이 없다. 동작 모형과 코드가 새 요청을 구현한다는 범위에서만 판단한다. 테스트 개수, 보고 양식, 문서 길이, 기록 비용은 창의성 점수가 아니다.
- 기준 문구를 제거한 동일 입력 재실행이 없다. 규칙이 없어도 같은 설계를 했을지, 특정 후보 해법을 버렸는지, 장기적으로 다른 담당자가 미검증 단계에 막힐지는 알 수 없다. S4에 새로 만든 규칙의 후속 효과도 관찰 구간 밖이다.

이 자료가 지지하는 제한된 결론은 **작업 중 규칙·완료 기준의 생성과 일부 문언상 과잉은 양쪽에서 발생했으며, JOENESS 조건에서는 기준이 공식 문서와 단계 상태로 지속되는 경로가 관찰됐다. 그러나 이번 네 새 담당자 변경 작업에서는 그 누적이 새 해법 변경·구현을 막았다는 결과는 없었다**는 것이다. 제품 수정이나 우열·보편적 안전성 판정으로 확대할 근거는 없다.
