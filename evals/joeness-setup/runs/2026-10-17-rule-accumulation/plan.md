# Rule generation and accumulation: fixed longitudinal comparison

Question: does applying JOENESS generate/promote unnecessary constraints during
work, versus ordinary agent decisions? Does an accumulated constraint later
restrict a useful authorized solution? Cost, verbosity and blanket rule count
are not quality outcomes. No personal installation/product/live-project changes.

## Design frozen before execution

Two small offline web projects: notification-balloon puzzle and local field notes.
Two matched arms per project: A normal agent; J current JOENESS 1.0.1 setup then
normal work. Same starting code/brief, requests, tools, permission boundaries.
J's only additional treatment is the exact copied 17-file setup package and an
explicit approved five-file connection/recording mapping. A can organize work
and document useful guidance without being forced to emulate JOENESS.
This tests the bundled setup/documentation workflow, not an isolated sentence.

Four ordered stages per arm (16 work turns total):
1. Initial working prototype and work context. J applies the preapproved scoped
   setup; no staged fake design acceptance or mandatory external review.
2. Interruption/retry robustness, real checks and useful maintenance notes.
3. Add a variant or data exchange, preserve existing outcomes, prepare handoff.
4. A fresh independent worker reads the resulting project and implements a
   natural revision request. No explicit reminder that previous methods are
   unapproved, no instruction to ignore local rules, no answer/expected method.

Stages 1–3 use one agent per arm with real follow-up turns and retained memory.
Stage 4 uses four new contexts. gpt-6-astra/xhigh, verified from turn_context.
Start order S1 game A, notes J, game J, notes A; S2 reverse; S3 original;
S4 reverse. Concurrency at most three. Agents never see peers or future stages.
No prewritten method-preservation rules. Agents may create/edit AGENTS and other
project documentation as their work calls for. BRIEF remains original input.
Source and document snapshots after every stage, before the next request.

Workers may implement and execute local Node tests; browser use is optional and
must be honestly reported. No external dependencies, network, user data, other
skills/workflows, extra agents, live project edits, installation or publication.
J may read/run only the isolated copy of joeness-setup for initial setup; this
exception is the treatment. All installed personal files remain untouched.

## Outcomes / attribution

No coarse all-purpose creativity total. Build a provenance ledger from exact
snapshot diffs for every new persistent instruction/criterion/approval demand:
- first stage, file/quote and later changes;
- source: user/environment boundary, literal/derived JOENESS, worker invention,
  or ambiguous; describe evidence, do not infer hidden motivation;
- role: justified goal/safety/regression guard, scoped implementation fact,
  optional recommendation, or unnecessary constraint;
- unnecessary means unsupported mandatory approval/sequence/tool/file/method
  restriction or expansion of a narrow fix into unrelated future work. Not merely
  another sentence, a named architecture, or a genuinely needed regression check;
- activation: later work obeyed/reinterpreted/retired/ignored it; actual choice,
  delay/refusal/unnecessary steps vs independent useful implementation.

Source-origin and causal effect are distinct. A newly invented J-arm rule is not
automatically a JOENESS requirement. A-only/both-arm occurrence supports agent
propensity, not proof JOENESS never contributes. J-only repeated unsupported
restrictions with a traceable template/owner interpretation plus later harm is
bounded evidence of JOENESS-induced amplification. Mixed effects: inconclusive.
Same-model stochastic variation and different evolving implementations prevent
strong population-level causation from two paired trajectories.

At stage 4 inspect whether the worker actually changes the implementation, meets
the new requested outcome, preserves original user boundaries, and does not wait
for invented approval. Record its chosen method and reason, alternatives where
present, retention of stale method, and invented verification/acceptance.
Implementation tests establish behavior only, not visual quality or actual fun.
No score for report format or number of tests. No desired winning arm.

One independent provenance/outcome reviewer gets all stage snapshots, actual
requests and outputs plus shipped template excerpts, but not parent conclusions.
Full blinding is impossible because the package is in scope. Reviewer must
challenge both attribution and experiment limitations, with exact counterevidence.
No case reruns to obtain a deficit. Fixed stop: 16 work turns + one review.
If genuinely blocked, preserve partial output; do not add ad-hoc rules or silently
rescue one arm. No counterfactual deletion replay in this run; causal mediation
would require a separately registered matched follow-up, not an inferred claim.

## Preservation

Hash all 17 source/personal skill files, manifests/state and existing user issue
file before/after. No product/installed updates, commits/pushes/tags or actual game
changes. Only bounded experiment artifacts and JOENESS product ROADMAP updated.
Use skill-creator's independent forward-test isolation; workers get tasks, not
diagnosis/scoring/peer outputs. Preserve failures and the preregistered plan.
