# 긴 맥락 재현 실험 설계 (15차, 초안)

## 왜
6차(상태 줄 누락)와 14차(새 작업을 무관한 TASK 항목에 이어 붙임)는 작은 고정 프로젝트에서 규칙 없이도 모두 통과했다.
같은 실패는 오목 실사용에서만 나왔다: TASK 61KB(이어 붙인 "추가 —" 문단 29개), ROADMAP 22KB, JOEFLOW state.json 244KB, 커밋 34개 분량의 세션.
가설: 규칙이 없어서가 아니라 긴 세션·큰 기록에서 규칙 준수가 약해진다. 그렇다면 문장 추가가 아니라 다른 장치가 필요하다.

## 1단계 — 재현 확인(파일럿, 이것이 통과해야 2단계 진행)
목표: 지금 최종본(B)으로 오목 규모 환경에서 같은 실패가 실제로 나오는지.
- 환경: 오목 저장소 실제 사본(기록 포함, 커밋 8f3bd88 기준). 시도마다 `git worktree`로 분리, `node_modules`는 공유 폴더 연결(각 190MB 복사 방지). 원본·오목 세션 작업 폴더는 건드리지 않음.
- 진행: 같은 에이전트에게 12턴을 순서대로 보냄(맥락 누적). 턴 구성은 오목에서 실패가 난 지점을 따라감.
  1. 상태 질문 / 2. 작은 버그 수정(ISSUES 연결) / 3. 디자인 시안 방향 승인 → 구현 시작(단계 전환) / 4~5. 구현 2건 / 6. 조사 메모(Library) / 7. 무관한 작은 설정 변경 / 8. 화면 수락 → 단계 마감(단계 전환) / 9. 다음 단계 첫 작업 / 10. 사용자 의견(근거 약함) / 11. 기록 금지 요청 작업 / 12. 오늘 정리 보고
- 측정(턴마다 기록 스냅샷을 떠서 기계 판정):
  - S1 상태 줄 최신성: 단계 제목·"현재/다음" 줄·항목 상태가 서로 맞는가(3·8턴 직후가 핵심).
  - S2 기록 단위: 새 작업이 자기 날짜·제목 항목에 들어갔는가, 기존 무관 항목 아래 "추가" 문단으로 붙었는가.
  - S3 중복: 같은 결정 요약이 TASK·ROADMAP에 반복되는가(결정 ID 언급 수 증가량).
  - S4 기존 규칙 회귀: 기록 금지(11턴)·의견 비판(10턴)·허위 완료 0 — 가린 판정자 1명이 12턴 묶음 채점.
- 시행: B × 2회. 판정 기준: 둘 중 하나라도 S1 또는 S2에서 실패하면 "재현됨".
- 재현 안 되면: 턴 수를 20으로 늘리거나 JOEFLOW 기획 작업(state.json 읽기·수정)을 섞어 부하를 키워 1회 더. 그래도 안 되면 "긴 세션 가설 기각" 기록 후 종료.

## 2단계 — 장치 비교(재현됐을 때만)
| 판 | 장치 | 성격 |
|---|---|---|
| B | 최종본 그대로 | 기준 |
| R | 블록에 1문장: "단계가 바뀌거나 작업을 마칠 때, 쓰기 전에 ROADMAP 현재 줄과 TASK 마지막 제목을 다시 읽는다." | 문장(가장 가벼움) |
| L | 기록 점검 스크립트(JOENESS가 제공하는 범용 검사): 상태 줄 불일치, 무관 항목 밑 이어 붙임, 크기 초과를 경고. 블록에 "작업을 마치면 기록 점검을 실행한다" 1문장 | 도구+문장 |
- 각 판 3회 × 12턴, 1단계와 같은 턴·측정.
- 채택 기준: S1·S2 실패율이 B보다 낮고 S4 회귀 0. 같으면 가벼운 쪽(R) 우선.
- L의 점검 스크립트는 특정 프로젝트 전용이 아닌 범용 규칙만 검사(제목 형식, 현재 줄과 항목 상태 대조, 파일 크기)하도록 만든다.

## 비용·한계
- 1회 = 12턴 × 맥락 누적이라 작은 실험 1회의 약 15~25배 토큰. 1단계 2회, 2단계 9회.
- 오목 세션과 같은 실제 기록을 쓰므로 그 세션이 기록을 고치면 기준 커밋을 고정해야 함(8f3bd88).
- 사용자 승인 턴(3·8턴)은 중계 메시지라 "승인으로 인정 안 함" 반응이 나올 수 있음(앞선 실험과 같은 한계) → 턴 문구에 "사용자 본인 메시지" 형식을 그대로 사용하고, 승인 미인정은 S1 판정에서 따로 분리.
