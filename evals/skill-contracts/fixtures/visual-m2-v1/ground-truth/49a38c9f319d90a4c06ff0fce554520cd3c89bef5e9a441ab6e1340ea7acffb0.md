## 2. 요약

사용자가 승인한 고해상도 컨셉은 서부식 쌍열 중절식 산탄총의 특징을 분명히 갖고 있었다.

- 넓고 평평한 호두나무 개머리판
- 개머리판에서 좁아지는 손목
- 짧고 묵직한 금속 리시버와 중절부
- 총열 아래의 분리된 목재 전방손잡이
- 길고 분리된 쌍열
- 상면에서 보이는 두 총열과 두 총구

그러나 실제 16×16 아이콘과 32×32 장착 아트로 옮긴 V2, V3, V4 후보는 이 구조를 보존하지 못했다. 후보들은 방향과 버전에 따라 드라이버, 막대, 파이프, 권총, 곤봉, 패들 또는 갈색 블록으로 읽혔다. 자동 테스트는 여러 차례 통과했고 일부 독립 리뷰도 잘못 통과했지만, 사용자가 기준 이미지와 직접 비교하자 시각적 불일치가 즉시 드러났다.

핵심 원인은 해상도 자체만이 아니다. 컨셉 아트는 픽셀아트처럼 보이는 고해상도 이미지였고, 네이티브 스프라이트에서는 부품별 정보가 한 픽셀 이하로 축소된다. 이때 단순 축소가 아니라 저해상도용 과장과 생략을 포함한 재디자인이 필요했다. 에이전트는 이를 충분히 이해하지 못한 채 행 배열 수정, 숫자 계약, 부품 마스크, 자동 추적을 연속 적용했다. 각 방법은 내부 구조의 존재를 증명했지만 최종 합성 이미지가 총처럼 보이는지는 증명하지 못했다.

프로세스상 가장 큰 실패는 다음과 같다.

1. 좌우 32×32 한 장을 먼저 완성하지 않고 아이콘과 모든 방향을 동시에 만들었다.
2. 사용자의 표현을 잘못 수치화해 상하 개머리판 폭을 최대 4픽셀로 제한했다.
3. 테스트가 최종 합성 픽셀의 가독성 대신 문자, 마스크, 폭, 행 수를 검증했다.
4. 일부 리뷰어가 숫자 계약 충족을 시각적 동일성으로 오판했다.
5. 루트 에이전트가 기준 이미지와 직접 비교하기 전에 리뷰 통과 결과를 사용자에게 제시했다.
6. 실패한 방법을 완전히 폐기하기 전에 유사한 변형을 반복했다.

향후에는 한 번에 하나의 시각 상태만 만든다. 첫 단계는 오직 동쪽을 향한 32×32 측면 아트 하나다. 이 한 장이 네이티브 크기와 8배 확대에서 사용자 승인을 받기 전까지 서쪽, 상하, 아이콘, 생산 통합으로 진행하지 않는다.

2026-08-11 후속 작업에서 이 원칙을 다시 위반한 별도 사고가 발생했다. 에이전트는 사용자가 준 간단한 4방향 기준 도안을 확보하고도 그 도안을 픽셀 단위로 전사하지 않았다. 대신 기존 고정 좌표와 수치 계약을 우선해 개머리판을 큰 갈색 덩어리로 만들고, UI 아이콘을 드라이버 또는 곤봉처럼 보이게 만들었다. 더 큰 문제는 결과 비교표 자체에 실패가 명확히 보였는데도 이를 내부 시각 검수 통과 후보로 취급하고 배포를 추천했다는 점이다. 이 후속 사고는 해상도나 도구의 한계가 아니라 에이전트의 검수 규칙 위반이다.

### 3.2 바인딩되는 총기 정체성

모든 방향과 크기는 다음 다섯 부품 순서를 공유해야 한다.

`개머리판 → 손목 → 리시버/중절부 → 전방손잡이 → 쌍열/두 총구`

각 부품이 코드에 존재하는 것만으로는 부족하다. 최종 합성 PNG에서 서로 구분되어 보여야 하며, 전체가 하나의 연결된 총으로 읽혀야 한다.

### 3.3 보호해야 할 시각 특징

- 개머리판은 평평한 뒤끝과 단계형 또는 완만한 테이퍼를 가진다.
- 손목은 개머리판과 리시버보다 명확히 좁다.
- 리시버는 세로 기둥이 아니라 짧고 묵직한 금속 중절부다.
- 전방손잡이는 총열 아래에 붙은 별도의 목재 덩어리다.
- 좌우 측면은 긴 총열과 총열 사이의 어두운 분리선 또는 리브를 유지한다.
- 상하는 평평한 개머리판, 짧은 목, 넓은 리시버, 두 레일, 두 총구를 유지한다.
- 아이콘은 세부 묘사를 줄여도 `큰 목재 뒤쪽 + 작은 금속 중심 + 긴 얇은 쌍열` 실루엣을 유지한다.

## 6. 기술적 원인

### 6.1 컨셉 아트는 실제 네이티브 픽셀 아트가 아니었음

컨셉은 큰 정사각 픽셀처럼 렌더됐지만 실제 캔버스는 16×16 또는 32×32가 아니었다. 총의 손목, 중절부, 방아쇠울, 전방손잡이와 쌍열 사이의 간격은 수십 개의 화면 픽셀로 표현됐다. 이를 네이티브 크기로 줄이면 많은 특징이 한 픽셀 이하가 된다.

따라서 컨셉은 형태와 재질의 기준이지, 축소 가능한 생산 소스가 아니다.

### 6.2 32×32 프레임 안의 실제 총기 예산을 잘못 배분함

32×32는 전체 캔버스다. 총 자체는 손 연결과 회전축 때문에 대략 폭 23~27, 높이 8 전후를 사용했다. 이 높이 안에서 개머리판, 손목, 리시버, 총열, 전방손잡이를 모두 사실적 비율로 축소하면 서로 겹친다.

네이티브 픽셀 아트에서는 다음을 의도적으로 과장해야 한다.

- 개머리판 높이와 테이퍼
- 손목의 잘록한 한 픽셀
- 리시버의 두께와 목재와의 명암 대비
- 전방손잡이와 총열 사이의 어두운 경계
- 쌍열 또는 리브 사이의 어두운 분리선

기존 작업은 실제 비율 축소에 가까웠고, 그 결과 부품들이 한 덩어리로 합쳐졌다.

### 6.3 축소와 재디자인을 혼동함

단순 축소는 면적 평균이나 최근접 샘플링으로 픽셀을 줄인다. 그러나 네이티브 스프라이트에는 의미 기반 결정이 필요하다.

- 방아쇠울을 생략할지 한 픽셀로 과장할지
- 손목을 한 픽셀 틈으로 표현할지 색 대비로 표현할지
- 두 총열을 실제 두 줄로 그릴지 한 줄과 리브로 암시할지
- 전방손잡이를 실제 비율보다 크게 만들어 목재 섬으로 보이게 할지

V4 자동 추적은 고해상도 가이드의 거친 실루엣은 가져왔지만 이런 의미 결정을 하지 못했다. 그래서 세부가 사라지고 블록으로 뭉쳤다.

### 6.4 방향별 아트를 공통 랜드마크에서 파생하지 않음

좌우와 상하가 동일한 총으로 보이려면 공통 랜드마크가 필요하다.

- 뒤끝
- 손목 중심
- 리시버 중심
- 전방손잡이 시작과 끝
- 총열 시작과 끝
- 총구 중심
- 캐릭터 손/회전축

V2는 각 방향의 행 배열을 사실상 독립 설계했다. V3는 마스크 이름은 공유했지만 최종 실루엣과 비율은 방향마다 달랐다. 그 결과 좌우는 파이프 총, 상하는 패들 또는 막대, 아이콘은 도구처럼 보였다.

### 6.5 잘못된 상하 개머리판 폭 제한

사용자의 요구는 컨셉 상면의 지나치게 넓고 삼각형인 개머리판을 좁히는 것이었다. 에이전트는 이를 최대 4픽셀로 수치화했다. 이 제한은 사용자에게서 나온 확정 규칙이 아니었으며, 상하 실루엣을 손잡이 또는 막대로 만드는 직접 원인이 됐다.

숫자 조건은 시각 목적을 보조해야 한다. 시각 목적을 파괴하는 숫자 조건은 폐기해야 한다.

### 6.6 팔레트와 경계 대비 부족

여섯 색 팔레트 자체는 충분할 수 있다. 문제는 배치였다.

- 리시버와 총열이 같은 회색 덩어리로 연결됨
- 전방손잡이가 총열 바로 아래 붙어 작은 갈색 선으로 보임
- 어두운 외곽선과 비교표 배경이 섞임
- 쌍열 사이의 분리선이 총열 명암에 묻힘

부품을 구분하려면 단순히 색 종류가 있어야 하는 것이 아니라, 최종 합성에서 경계 픽셀이 보존되어야 한다.

## 7. 테스트와 리뷰 실패 원인

### 7.1 V2 테스트의 문제

V2 테스트는 다음을 검증했다.

- 특정 행에 목재 색이 있는가
- 개머리판보다 손목이 좁은가
- 금속 리시버가 있는가
- 전방손잡이와 쌍열 문자가 존재하는가
- 방향별 미러와 팔레트가 맞는가

이 검사는 부품의 존재를 증명하지만 최종 이미지에서 각 부품이 구분되어 보이는지는 증명하지 않는다.

### 7.2 V3 테스트의 문제

V3는 부품을 별도 마스크로 만들었지만 테스트는 합성 전 마스크의 크기와 좌표를 주로 검증했다. 이후 레이어가 앞의 마스크를 덮거나 서로 붙어서 하나의 덩어리로 보여도 테스트가 통과했다.

마스크 분리는 소스 구조의 품질이다. 최종 시각 분리는 렌더 결과의 품질이다. 둘은 같은 검증이 아니다.

### 7.3 V4 테스트의 문제

V4는 다음을 객관적으로 검증했다.

- 배경 누출 없음
- 허용 팔레트만 사용
- 연결된 실루엣
- 대각선 또는 방향별 크기
- 결정론적 출력

그러나 연결된 실루엣이 총인지 도끼인지 구분하지 못한다. 자동 축소 결과의 기술적 유효성과 총기 정체성은 별개다.

### 7.4 독립 리뷰의 잘못된 통과

V2 수정 3에서 리뷰어는 `개머리판 → 손목 → 리시버 → 전방손잡이 → 쌍열` 체인이 존재한다는 이유로 PASS를 줬다. 사용자가 기준 이미지와 직접 비교하자 전혀 같은 총이 아니라는 점이 드러났다.

검토자는 계약 준수와 시각 동일성을 분리했어야 한다. 루트 에이전트도 리뷰어 판정을 그대로 전달하기 전에 기준 이미지와 최종 확대본을 직접 대조했어야 한다.

## 8. 에이전트의 실책

아래 항목은 해상도 한계가 아니라 에이전트의 판단 및 집행 실패다.

### 8.1 한 번에 너무 많은 상태를 구현함

아이콘, 좌우, 상하, 조준, 발사를 한 작업으로 만들었다. 첫 측면 실루엣조차 승인되지 않았는데 파생 방향을 만들어, 잘못된 형태가 네 방향과 테스트에 확산됐다.

### 8.2 사용자 요구를 임의의 숫자로 고정함

상하 개머리판 최대 4픽셀은 사용자 요구를 잘못 번역한 값이었다. 이 값을 테스트로 강제해 이후 에이전트가 시각적으로 더 나은 폭을 선택하지 못하게 했다.

### 8.3 자동 통과를 시각 통과로 과대해석함

결정론, 팔레트, 픽셀 수, 미러 검사는 모두 필요하지만 총처럼 보이는지를 증명하지 않는다. 에이전트는 자동 GREEN과 시각 수락을 반복해서 섞었다.

### 8.4 자기 검토 문구가 실제 이미지와 충돌함

구현 보고서는 후보를 `full-stock`, `same weapon`, `plainly shotgun`이라고 표현했지만 최종 확대본은 막대 또는 도구로 보였다. 보고서가 증거보다 낙관적이었다.

### 8.5 루트가 사용자 게이트 전에 충분히 차단하지 못함

V2 수정 3은 독립 리뷰가 PASS한 뒤 사용자에게 제시됐다. 루트가 같은 기준 이미지와 확대본을 직접 나란히 보고 한 문장으로 형태를 설명했다면 통과시키지 않았어야 한다.

### 8.6 실패한 가설을 변형해 반복함

- 행 배열 수정
- 행 배열 전면 재작성
- 숫자 조건 강화
- 부품 마스크 분리
- 자동 추적

각 방법은 이름이 달랐지만, 최종 합성 이미지의 총기 인식성을 먼저 승인받지 않고 여러 방향을 한꺼번에 생성한다는 공통 실패를 반복했다.

### 8.7 고정해야 할 섬광 좌표를 후보에 맞춰 이동함

`61aa0f8`은 더 긴 미리보기 총구에 맞춰 좌우 섬광 좌표를 이동하고 테스트도 새 위치를 허용하도록 바꿨다. 아트가 기존 손·총구·투사체 계약에 맞아야 했으며, 계약을 아트에 맞춰 이동하면 안 됐다.

### 8.8 임시 첨부 경로를 재현 가능한 참조로 사용함

초기 빌더와 테스트는 `AppData/Local/Temp` 경로를 직접 참조했다. 임시 파일이 사라지면 비교표를 재생성할 수 없다. 이후 V3에서 캐시했지만 처음부터 프로젝트 소유 참조 묶음이 필요했다.

### 8.9 사용자의 검토 비용을 늘림

내부에서 명백히 도구처럼 보이는 후보를 사용자에게 보여줬다. 사용자는 기준 이미지와 후보의 차이를 다시 설명해야 했다. 시각 후보는 사용자에게 올리기 전에 내부에서 최소한 `이 물체를 처음 보는 사람이 무엇이라고 부를지` 검토를 통과해야 한다.

## 9. 기존 접근별 평가

### 9.1 전체 행 배열 방식 — 폐기

장점:

- 단순하고 결정론적
- 팔레트와 미러 테스트가 쉬움

실패 이유:

- 한 부품 수정이 같은 행의 다른 부품 형태를 바꿈
- 방향별 같은 총기 구조를 공유하기 어려움
- 숫자 행 계약이 시각적 총기 정체성을 대체함

재사용 조건:

- 승인된 네이티브 픽셀 원화를 직렬화하는 용도로만 사용 가능
- 원화를 설계하는 도구로는 사용 금지

### 9.2 부품 마스크 방식 — 설계 도구로는 보류

장점:

- 부품 책임과 합성 순서가 명확함
- 공통 랜드마크와 방향 파생에 사용할 수 있음

실패 이유:

- 마스크를 수치로 만들었고 최종 합성 가독성을 검증하지 않음
- 서로 분리된 소스 마스크가 최종 이미지에서 다시 붙음

재사용 조건:

- 먼저 수작업으로 승인된 완성 픽셀이 있어야 함
- 마스크는 승인 픽셀을 분해·재사용하는 구현 도구로만 사용

### 9.3 자동 추적·축소 방식 — 생산 원화 생성용으로 폐기

장점:

- 고해상도 기준의 거친 비율을 빠르게 옮김
- 결정론적 축소와 팔레트 양자화 가능

실패 이유:

- 부품 의미를 알지 못해 손목, 리시버, 전방손잡이, 쌍열을 평균화함
- 실루엣은 연결됐지만 총기 정체성이 사라짐

재사용 조건:

- 수작업 시작점 또는 배경 제거 실험으로만 사용
- 사용자에게 보여줄 후보나 생산 아트로 직접 사용 금지

## 10. 개선된 진행 원칙

### 원칙 1 — 네이티브 픽셀부터 설계

컨셉 아트를 줄이지 않는다. 처음부터 실제 32×32 캔버스에서 어떤 픽셀을 과장하고 생략할지 결정한다.

### 원칙 2 — 한 번에 하나의 상태만 승인

진행 순서는 고정한다.

1. 동쪽 32×32 측면 조준 몸체
2. 서쪽은 승인된 동쪽의 정확한 미러
3. 남쪽 32×32 평면도
4. 북쪽은 승인된 남쪽에서 공통 랜드마크로 파생
5. 16×16 아이콘은 별도 상징화
6. 발사 섬광 프레임
7. 생산 통합
8. 게임 내 수락

앞 단계가 사용자에게 수락되지 않으면 다음 단계로 진행하지 않는다.

### 원칙 3 — 공통 랜드마크 표를 먼저 승인

동쪽 측면을 그리기 전에 다음 좌표와 픽셀 예산을 문서화한다.

| 부품 | 목표 역할 | 확인 기준 |
|---|---|---|
| 개머리판 | 가장 큰 목재 덩어리 | 평평한 뒤끝, 위아래 비대칭 테이퍼 |
| 손목 | 가장 좁은 연결부 | 개머리판/리시버보다 명확히 좁음 |
| 리시버 | 금속 중심 질량 | 총열보다 두껍고 세로 기둥이 아님 |
| 전방손잡이 | 별도 목재 섬 | 총열 아래 붙지만 경계 한 픽셀 보존 |
| 쌍열 | 긴 전방 실루엣 | 분리선 또는 리브가 연속적으로 보임 |
| 총구 | 발사 기준점 | 기존 섬광·투사체 좌표와 일치 |

숫자는 시각 목표를 훼손하지 않는 범위에서만 정한다.

### 원칙 4 — 아이콘은 축소판이 아니라 별도 심벌

16×16 아이콘은 32×32 장착 아트를 자동 축소하지 않는다. 같은 팔레트와 부품 순서를 공유하되 다음 세 덩어리를 우선한다.

- 큰 목재 개머리판
- 짧고 어두운 금속 중심부
- 길고 얇은 밝은 총열

방아쇠울, 힌지, 세부 명암은 이 세 덩어리가 분명한 경우에만 추가한다.

### 원칙 5 — 최종 합성 픽셀을 검증

소스 마스크가 아니라 실제 생성된 PNG를 검사한다.

- 최종 이미지에서 남은 각 색상 영역의 크기
- 개머리판과 리시버가 한 덩어리로 합쳐졌는지
- 전방손잡이가 총열과 분리되어 보이는지
- 쌍열 분리선이 최종 픽셀에 남는지
- 방향별 공통 랜드마크 비율
- 투명 배경과 외곽선 보존

다만 이 자동 검사는 시각 수락을 대체하지 않는다.

### 원칙 6 — 후보 상태를 명확히 표시

모든 결과는 다음 중 하나로 표시한다.

- `draft`: 구현자 자체 검토 전
- `internal candidate`: 내부 기준 이미지 비교 통과
- `user candidate`: 사용자에게 제시할 수 있는 상태
- `accepted art`: 사용자 직접 수락
- `production candidate`: 생산 통합 후 게임 내 검증 대기
- `accepted production`: 게임 내 사용자 수락

자동 테스트 통과만으로 `accepted`라는 표현을 사용하지 않는다.

## 11. 새 승인 게이트

### Gate A — 동쪽 측면 원화

필수 산출물:

- 32×32 투명 PNG
- 8배 최근접 확대 PNG
- 픽셀 격자가 표시된 확대본
- 기준 측면 이미지와 나란한 비교표
- 개머리판, 손목, 리시버, 전방손잡이, 총열, 총구 좌표 표

판정 질문:

1. 처음 보는 사람이 장총 또는 쌍열 산탄총으로 읽는가?
2. 개머리판이 갈색 사각 블록이 아니라 어깨용 개머리판으로 보이는가?
3. 리시버가 세로 기둥 또는 파이프 연결부처럼 보이지 않는가?
4. 전방손잡이가 별도 목재 부품으로 보이는가?
5. 총열이 회색 막대 하나로 보이지 않는가?

한 항목이라도 실패하면 다른 방향을 만들지 않는다.

### Gate B — 방향 일관성

남쪽 평면도를 만든 뒤 측면과 나란히 비교한다.

- 뒤끝에서 총구까지의 부품 비율이 같은가?
- 손목과 리시버 위치가 대응하는가?
- 전방손잡이 길이가 대응하는가?
- 두 총구가 명확한가?
- 같은 총의 다른 투영으로 보이는가?

### Gate C — 아이콘

아이콘은 네이티브 16×16, 4배 UI 크기, 실제 인벤토리 슬롯 목업 세 상태에서 검토한다. 확대본만 통과해서는 안 된다.

### Gate D — 생산 통합

모든 아트 수락 뒤에만 생산 PNG와 빌더를 변경한다. 기존 총구·손·섬광·투사체 좌표를 아트에 맞춰 이동하지 않는다. 아트가 고정 계약에 맞아야 한다.

### Gate E — 게임 내 수락

- 인벤토리 슬롯
- 툴팁
- 동서남북 정지 조준
- 동서남북 조준 걷기
- 지향사격
- 조준 발사와 섬광
- 총구와 투사체 시작점

각 상태를 사용자에게 수정 항목과 미검증 항목으로 분리해 제공한다.

## 12. 테스트 개선안

### 12.1 유지할 자동 계약

- 정확한 캔버스 크기

## 17. 결론

이번 실패는 좋은 컨셉이 없어서 발생하지 않았다. 컨셉은 충분히 명확했다. 실패는 고해상도 컨셉의 의미를 네이티브 픽셀로 재설계하지 못하고, 수치와 구조의 존재를 최종 시각 가독성으로 오해한 데서 발생했다.

16×16과 32×32에서도 산탄총은 표현할 수 있다. 다만 축소, 자동 추적, 마스크 존재 검사가 대신 설계해주지는 않는다. 먼저 한 장의 네이티브 측면 원화를 사람의 시각 기준으로 완성하고, 그 원화에서 다른 방향과 아이콘을 단계적으로 파생해야 한다.

### 18.2 직접 원인

사용자 기준 이미지의 동쪽 총을 논리 픽셀로 역추출하면 정확히 20×6이다.

```text
....OOOOOOOOOOOOOOOO
.OOOLDDMOMMMMMMMMMMM
OWWWLDDMOOOOOOOOOOOO
OWWWLDDMOWWWWWO.....
OWLOOOOOOOOOOOO.....
.OO.................
```

이 배열은 전체를 채운 갈색 개머리판이 아니다. 왼쪽 4칸 안에서 개머리판이 빠르게 가늘어지고, 그 다음 4칸에 리시버가 있으며, 나머지 12칸을 긴 총열이 차지한다. 실패한 `2043004` 후보는 개머리판 영역을 약 9칸짜리 채운 질량으로 확장해 이 비율을 역전시켰다.

직접 원인은 다음 네 가지다.

1. **기준 이미지 미전사** — 이미지가 충분히 단순했는데도 픽셀 그리드를 먼저 읽지 않고 기억과 추정으로 다시 그렸다.
2. **좌표 계약의 과잉 우선** — 동쪽 손 기준 `(13,16)`과 총구 `(22,16)`을 보존하는 수치가 시각 기준보다 우선됐다. 이 제약은 손과 총구 사이를 9픽셀로 고정하므로 기준의 긴 총열 비율과 충돌할 수 있지만, 에이전트는 충돌을 보고하지 않고 개머리판을 채워 숨겼다.
3. **객관 테스트와 의미 판정 혼동** — 팔레트, 폭, 부품 픽셀 수, 해시, 빌드 성공은 검증했지만 최종 이미지가 총으로 읽히는지는 검증하지 못했다.
4. **최종 산출물 직접 검토 누락** — 비교표를 생성한 뒤 기준과 후보를 나란히 보고도 명백한 실루엣 차이를 실패로 처리하지 않았다.

좌표 제약은 설계를 어렵게 만든 보조 원인이다. 사용자 기준을 갈색 블록으로 왜곡한 직접 원인은 엔진이나 JOENESS가 아니라 에이전트의 판단과 실행이다.

### 18.4 JOENESS가 끼친 영향과 한계

JOENESS의 원칙 자체가 이 실패를 지시한 것은 아니다. 오히려 다음 규칙은 사고를 막는 방향이었다.

- 자동 결과와 실제 관찰을 구분한다.
- `fixed`는 원래 실패를 직접 재검증했을 때만 사용한다.
- 배포와 같은 공유 쓰기 전후 상태를 확인한다.
- 파일명, 로그 문구, 프로세스 생존을 성공 근거로 삼지 않는다.
- 검증 범위와 남은 위험을 명시한다.

문제는 에이전트가 이 규칙을 시각 작업에 제대로 적용하지 않았다는 점이다. `visual-check`도 네이티브 크기, 확대본, 최소 사용 맥락을 직접 보도록 요구했지만, 에이전트는 수치 계약과 생성 완료 메시지를 사실상의 검수로 대체했다. 따라서 본 사고에서 JOENESS의 직접 기여는 낮고, 에이전트의 규칙 위반 기여가 높다.

다만 JOENESS/하네스에는 보완할 지점이 있다.

1. 시각 산출물에 대해 `미검수 → 내부 실패 → 내부 통과 → 사용자 통과` 상태를 강제로 분리하지 않는다.
2. `view_image`로 실제 산출물을 열었다는 증거와 판정 근거를 완료 조건으로 강제하지 않는다.
3. 객관 테스트 GREEN이 시각 승인 문구로 승격되는 것을 자동 차단하지 않는다.
4. 대표 한 장이 사용자에게 수락되기 전 미러·아이콘·생산 통합로 확산되는 것을 구조적으로 막지 않는다.
5. 긴 영상 프레임 분석이나 넓은 과거 증거 탐색에서 120초 같은 고정 실행 제한은 충분하지 않을 수 있다. 무제한 실행이 해법은 아니지만, 진행 증거가 있고 범위가 명확한 읽기 작업에는 단계별 연장 또는 체크포인트 재개가 필요하다. 이번 아트 사고는 시간 부족이 원인이 아니지만, 과거 상태 복원·영상 분석 사고에서는 성급한 결론을 유도할 수 있다.

### 18.5 에이전트의 실책

JOENESS/하네스의 부족과 별도로, 다음은 전적으로 에이전트의 실책이다.

1. 사용자 기준 이미지를 픽셀 단위로 읽지 않았다.
2. 기준보다 큰 개머리판과 짧은 총열을 만들고도 `비슷하다`고 판단했다.
3. 아이콘이 드라이버·곤봉처럼 보이는데도 바닐라 친화 후보로 제시했다.
4. 비교표에 실패가 드러났는데도 배포 추천 단계까지 진행했다.
5. 내부 시각 검수를 사용자가 대신하도록 만들었다.
6. 거절된 방식의 행 배열을 이름만 바꿔 반복했다.
7. 생산 소스, 배포본, 사용자 판정을 한 문장 안에서 혼용했다.
8. 버전 원장 갱신보다 다음 후보 생성을 우선했다.

### 18.6 개선안에 대한 의견

내 의견으로는 이 문제를 더 많은 디자인 도구나 더 복잡한 테스트로 해결하면 안 된다. 핵심 개선은 상태 전이와 책임을 단순하게 강제하는 것이다.

1. **기준 이미지 고정** — 사용자 기준 이미지를 프로젝트 소유 경로로 복사하고 SHA-256을 기록한다.
2. **픽셀 전사 우선** — 기준이 이미 저해상도면 먼저 정확한 논리 픽셀 배열을 추출한다. 창작적 재해석은 사용자가 요청한 변화만 적용한다.
3. **대표 한 장 게이트** — 동쪽 하나가 내부·사용자 검수를 통과하기 전 서쪽, 상하, 아이콘, 생산 통합을 금지한다.
4. **3종 시각 증거 강제** — 네이티브, 최근접 확대, 실제 캐릭터 크기 맥락 이미지를 모두 열어 본 뒤 판정한다.
5. **테스트 표현 제한** — 자동 테스트 출력에는 `visual accepted`, `same weapon`, `fixed`를 사용할 수 없게 하고 `objective contract only`만 허용한다.
6. **루트 직접 검수** — 구현자나 리뷰어가 PASS를 줘도 최종 제시자는 기준과 후보를 직접 비교한다.
7. **배포 원장 원자화** — 배포가 끝난 같은 작업에서 커밋, 파일 해시, 사용자 판정 대기 상태를 원장에 기록한다.
8. **시간 제한의 증거 기반 완화** — 120초 초과가 예상되는 읽기 전용 분석은 범위·진행률·체크포인트가 확인될 때만 연장하고, 쓰기 작업은 기존 제한을 유지한다.

### 18.8 제출 직후 재발한 검수 오류와 정정

첫 제출 직후 사용자는 캐릭터 크기 합성본의 총이 골반 부근에 배치됐다고 지적했다. 지적은 정확했다.

초기 합성 스크립트는 32×32 셀의 좌상단을 캔버스 `(400,118)`에 두었다. 총의 실제 비투명 행은 소스 `Y=13..18`이므로 4배 확대 후 화면 `Y=170..193`에 나타났다. 이는 미러링된 농부 스크린샷의 손·어깨가 아니라 허리·골반 대역이다. 에이전트는 이 이미지를 직접 열어 보고도 위치 오류를 발견하지 못하고 내부 시각 통과라고 보고했다.

이 오류는 다음과 같이 정정했다.

- 합성 셀 좌상단 Y: `118 → 98`
- 실제 비투명 표시 대역: `170..193 → 150..173`
- 새 위치 계약: 후보의 소스 픽셀 `(0,15)`가 합성 캔버스 `(404,158)`의 외곽색과 일치해야 함
- 비교 기준: 사용자가 제공한 실제 동쪽 조준 스크린샷의 총열 높이

이 사건은 18.4~18.6의 결론을 더 강하게 만든다. 단순히 `view_image`를 호출하거나 이미지를 열었다는 사실만으로는 검수가 아니다. 검수자는 반드시 `손 접점`, `어깨 높이`, `총구 위치`, `몸 대비 크기`처럼 관찰 항목별 판정을 남겨야 한다. 시각 게이트를 통과시킨 뒤 사용자가 즉시 발견할 정도의 배치 오류가 남았다면 해당 게이트는 실행된 것이 아니라 형식적으로 소비된 것이다.

### 18.9 방향별 크기 비교 후 축소

수정된 손 높이 합성본을 기존 상·하 총기 프레임과 같은 게임 픽셀 배율로 비교했다. 기존 상·하는 각각 `6×16` 논리 픽셀이고 최초 동쪽 초안은 `22×6`이었다. 즉 좌우 총의 주축 길이가 상·하보다 37.5% 길었으며, 화면 배율 4 기준 `88px 대 64px`였다.

사용자는 디자인은 유지하되 개머리판과 총열 양쪽에서 조금씩 줄이라고 지시했다. 이에 다음처럼 축소했다.

- 전체: `22×6 → 19×6`
- 개머리판 쪽: 1논리 픽셀 축소
- 총열·전방손잡이 쪽: 2논리 픽셀 축소
- 캐릭터 합성 X: `400 → 404`, 리시버·손 접점의 화면 위치 보존
- 상·하 대비 주축 길이 차이: `37.5% → 18.75%`

축소 후 네이티브, 8배, 손 높이 캐릭터 합성, 동일 배율 방향 비교표를 다시 열어 확인했다. 개머리판-리시버-총열-전방손잡이 구분은 유지됐으며 이전 22픽셀 후보보다 몸 대비 길이가 줄었다. 이 역시 미리보기 단계이며 생산·배포 파일은 변경하지 않았다.

사용자가 빨간 박스로 지정한 돌출은 전방손잡이 끝 외곽 `(14,16)`이 아니라 한 줄 아래의 우측 끝 외곽 `(15,17)`이었다. `(14,16)`은 보존하고 `(15,17)`만 `O → .`로 바꿨다. 계약 테스트도 두 좌표를 각각 `보존`과 `제거`로 고정해 같은 오인 수정을 반복하지 않도록 했다.

### 18.10 동쪽 승인 후 서쪽 미러와 아이콘 게이트

### 18.11 바닐라 측정 없이 정한 14×6 아이콘 기준 폐기

사용자가 바닐라 무기와 도구의 실제 크기를 먼저 측정하라고 지적한 뒤, Stardew Valley 1.6.15의 `tools.xnb`와 `weapons.xnb`를 16×16 셀 단위로 직접 측정했다. 무기 67개 중 38개가 16×16 전체 가시 영역을 사용했고, 47개는 폭 15픽셀 이상, 48개는 높이 15픽셀 이상이었다. 기본 도구 행 90개 중 89개도 높이 14픽셀 이상이었다.

이 증거는 직전 14×6 수평 아이콘 후보의 기준이 잘못되었음을 확정한다. 에이전트는 바닐라 자산을 먼저 측정하지 않고 `아이콘은 작고 여백이 많아야 한다`는 임의 전제를 세웠다. 그 결과 승인된 장총 콘셉트를 16×16 셀 안에서 대각선으로 재구성하지 않고, 월드용 측면 스프라이트를 축소한 듯한 짧은 도구 모양을 반복해서 만들었다. 이는 JOENESS나 도구의 강제가 아니라 에이전트의 측정 순서와 시각 판정 실패다.

개선된 순서는 다음과 같다.

1. 대상 게임의 실제 동일 용도 자산을 네이티브 픽셀로 추출하고 경계 상자를 측정한다.
2. 사용자 승인 콘셉트에서 식별에 필요한 부품만 우선순위로 고정한다.
3. 실제 슬롯 문법에 맞는 구도에서 새로 픽셀화한다. 월드 스프라이트를 아이콘으로 단순 축소하지 않는다.
4. 네이티브, 최근접 확대, 실제 슬롯, 바닐라 비교표를 모두 직접 확인한다.
5. 자동 검사는 크기와 부품 존재만 보호하며, 시각 승인으로 간주하지 않는다.
6. 사용자 승인 전에는 생산 아틀라스와 배포본을 변경하지 않는다.

현재 후보는 16×16 전체 대각선을 사용하고, 왼쪽 아래의 각진 목재 개머리판에서 손목·강철 리시버·목재 전방손잡이·오른쪽 위의 긴 총열 순서를 유지한다. 객관 계약과 내부 비교는 통과했지만 사용자 시각 승인은 아직 받지 않았고, 생산 및 배포 파일은 변경하지 않았다.

### 18.12 경계 상자 통과를 시각 통과로 오판한 후보 폐기

18.11 직후 만든 후보는 `x=0..15`, `y=0..15` 경계와 모서리 접촉을 강제했다. 자동 검사는 통과했지만 실제 슬롯에서는 개머리판·리시버·전방손잡이·총열이 굵기 변화 없이 한 대각선으로 합쳐졌고, 밝은 총열 끝까지 뾰족하게 보여 샷건이 아니라 칼이나 창처럼 읽혔다. 에이전트가 이 이미지를 직접 보고도 바닐라와 크기가 맞는다는 이유로 통과시킨 것은 명백한 시각 판정 실패다.

원인은 바닐라 측정값 중 경계 상자만 사용하고 다음 항목을 판정하지 않은 것이다.

- 개머리판의 실제 면적과 어깨에 닿는 넓은 후단
- 개머리판·리시버·총열 사이의 굵기 단계
- 리시버 아래 방아쇠울과 총열 아래 목재 전방손잡이의 분리
- 칼날처럼 뾰족하지 않은 총구 실루엣
- 확대가 아닌 실제 슬롯에서의 무기 종류 식별성

해당 후보는 폐기했다. 교정안은 모서리 접촉을 제거하고 `16×11` 가시 영역을 사용한다. 넓은 목재 개머리판, 짧은 강철 리시버, 분리된 목재 전방손잡이, 긴 강철 총열과 작은 방아쇠울을 서로 다른 굵기로 배치했다. 네이티브·8배·실제 슬롯·바닐라 동급 비교를 다시 수행했으며, 생산 아틀라스와 Mods 배포본은 여전히 변경하지 않았다. 이 교정안 역시 사용자 시각 승인 전에는 생산 후보일 뿐 최종본이 아니다.

### 18.13 사용자 픽셀 도안을 재해석하지 않고 직접 축약

사용자는 에이전트가 계속 새 실루엣을 발명하는 대신 따라야 할 구체적인 픽셀 도안을 제공했다. 원본은 471×477 확대 이미지였고, 32×32 논리 격자와 다섯 색상(`O`, `M`, `D`, `W`, `L`)을 정확히 복원할 수 있었다. 원본 이미지 SHA-256은 `0275E0DF6B706EABC646D5F158CB415115ED47E6804B606952966207719FC0A0`이며, 복원한 논리 도안은 `art/reference/shotgun-user-icon-2026-08-11/reference-32.pixelmap`에 고정했다.

직전 16×11 후보가 실패한 이유는 사용자가 형태를 이미 제시했는데도 에이전트가 이를 참고자료 정도로 취급하고 별도의 개머리판·기관부·총열 비율을 다시 설계했기 때문이다. 이번에는 32×32 도안을 2×2 논리 셀 기준으로 축약하고, 16×16에서 사라지는 외곽선과 개머리판 면적만 복구했다. 결과는 `x=0..15`, `y=0..14`의 16×15 가시 영역이며, 원본 32×32와 후보 16×16을 동일 화면 크기로 직접 비교하는 `user-reference-icon-comparison.png`를 렌더러와 테스트 산출물에 추가했다.

객관 계약, 두 번의 결정론 생성, 원본-축약본 동배율 비교, 실제 슬롯 검토를 통과했다. 생산 아틀라스와 Mods 배포본은 변경하지 않았고 사용자 시각 승인 전에는 후보 상태를 유지한다.
