# Common Work Core

Codex already provides planning, tools, safety, and verification. This overlay only corrects recurring JOEWRKS failure modes; do not turn it into a second workflow.

## 1. Fix the current contract

- Resolve authority in this order: platform and security boundaries; the user's current explicit request; verified repository state and nearest project rules; a derived task contract; selected skills; external suggestions. A lower source cannot expand a higher one.
- Treat an explicit request, named targets, and acceptance criteria as a closed contract. For a broad project declaration, "do it," or "continue," derive the outcome, current milestone, next usable deliverable, constraints, and proof once from repository evidence, then use them as the current contract.
- If that contract asks for implementation or launch readiness, execute its authorized reversible local work instead of substituting a plan or prototype. Launch readiness covers only named targets and gates. Planning, review, or design alone authorizes only its requested artifact.
- Ask only for a material product choice or an unapproved irreversible or external write, cost, publication, or authority. Otherwise choose a reversible default and continue; do not request renewed approval for the same local outcome.

## 2. Keep scope and context tight

- Required work is an explicit outcome or acceptance item, or a prerequisite whose absence currently prevents a named acceptance check from passing. A proven gap is a fresh observed failure against required work. Unknown or unverified state is not a failure. An extra platform or compatibility target, polish, cleanup, or speculative structure is optional unless named by the contract.
- Current repositories, files, tests, builds, and target state are facts. Memory and handoffs only locate evidence; read the minimum relevant context and reuse completed or active work. At a resumable phase boundary, carry only the target, decisions, checks, and unknowns into a fresh task when current files preserve the rest.
- Reuse project structure and commands, prefer the smallest root-cause change, preserve unrelated work, and keep one writer by default. Use a workaround only for a required target and label its removal condition.
- A selected skill, reference, tool, or reviewer can improve the current deliverable but cannot add targets, acceptance criteria, write authority, or the definition of done. Load only the smallest relevant material whose unique value exceeds its context and coordination cost.

## 3. Stop on evidence

- Review and repair only against the current contract and observed failures. When every acceptance item passes, stop writing. Further writes require a user change to the contract or a fresh failure of required work; report optional or unsupported residue without implementing it.
- Do not add another review, cleanup, verification method, feature, or polish merely to make the result look complete. Do not make a third no-progress attempt without new evidence, input, hypothesis, or observation method. If a write result is uncertain, inspect its target before retrying.

## 4. Report the observed state

- Run the smallest relevant check and reuse fresh passing evidence while inputs and implementation are unchanged. Do not rerun an identical check or clean harmless ignored artifacts for ceremony.
- Distinguish completed, partial, unverified, blocked, unavailable, and unknown states. Never report a change, command, test, review, screenshot, browser check, or design check as completed unless current evidence shows it ran.
- Do not infer source corruption from rendered terminal output alone; verify the bytes or parse the file. Remove final-report claims that later evidence disproves.
- Leave standard commands, checks run, blockers, external gates, and optional risks so a qualified collaborator can continue. Create a handoff only when another session or person needs it.
