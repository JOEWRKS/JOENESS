# JOENESS 0.3

배포 버전은 `0.3.1`, 이 브랜치의 출시 후보는 `0.3.2`입니다. 아직 배포하지 않았습니다. 지원 범위는 Windows PowerShell·Git 프로젝트·Codex입니다. 개인 설치와 기존 프로젝트 연결은 자동 갱신되지 않습니다. 배포 상태는 [현재 작업과 출시 기록](docs/ROADMAP.md)에서 확인합니다. 보편적인 성능 향상이나 토큰 절감은 주장하지 않습니다.

## 핵심 — 세줄요약

1. 프로젝트의 목표와 승인된 구현 단계·완료 기준을 단계별 로드맵으로 정리합니다.
2. 문서를 역할별로 나누되 작업별 읽기 우선순위로 연결해, 정보 단절과 기준 혼동을 줄입니다.
3. 작업 결과를 여섯 항목으로 먼저 보고해, 핵심 누락과 중언부언을 줄이도록 설계했습니다.

실제 작업·인수인계 뒤에는 `작업 · 업데이트 파일 · 이슈 · 해결 · 남은 문제 · 다음 작업`을 쉬운 말로 한 줄씩 먼저 보고합니다. `이슈`는 발생한 문제, `해결`은 확인된 조치, `남은 문제`는 미해결·미검증을 뜻합니다. 여섯 줄로 판단에 필요한 원인·근거·승인 경계를 담지 못할 때만 `상세 보고`를 덧붙이며, 단순 질문에는 이 양식을 강제하지 않습니다.

설치되는 공개 도구는 프로젝트 설정용 `joeness-setup` 하나입니다.

### 0.3.2 변경 사항 — 출시 준비

- 문서마다 담당 정보와 갱신 책임 명시. 목표·완료 기준·현재 상태는 로드맵에서 함께 관리.
- 실제 작업 뒤 작업 기록과 영향받은 로드맵 상태·다음 작업을 함께 갱신.
- 결과·근거·미완·원인은 보존하고, 반복 설명은 줄여 원본으로 연결.
- 기존 문서 재편은 승인 후 진행. 새로운 전역 규칙이나 자동 갱신 기능은 추가하지 않음.

### 0.3.1 변경 사항

- 로드맵이 없으면 작은 로드맵을 기본 제안. 기존 계획 문서가 있으면 재사용하며 적용 전 승인.
- 구현 순서, 단계 진입·종료 조건, 필수 검증을 각각 체크 항목으로 구분.
- 다음 작업을 정하기 전에 기존 완료 근거 확인. 변경되거나 검증이 빠진 부분만 다시 검사.
- 연결 상태 확인과 로드맵 내용 검증을 구분. 사용자 수락은 별도 유지.

여섯 항목 보고와 setup-only 구성은 유지합니다. 기존 실패 기록은 보존하며, 모든 상황에서 누락을 방지한다는 보장은 하지 않습니다.

## 설계 목적

프로젝트가 길어지면 목표와 완료 기준이 개별 작업에 묻히고, 같은 사실이 여러 문서에 중복되거나 오래된 인수인계가 현재 상태처럼 읽히기 쉽습니다. 작업 하나를 마쳤다는 이유로 필수 검증이나 사용자 수락이 남은 단계까지 완료로 오해할 수도 있습니다. 긴 작업 설명은 사용자와 다음 담당자가 **무엇을 했고 무엇이 남았는지** 다시 찾아야 하는 부담을 만듭니다.

JOENESS는 기존 문서와 제품 기준을 우선 사용하고, 같은 사실은 주된 원본 한 곳에 남긴 뒤 다른 문서에는 위치만 연결합니다. 승인된 단계가 있다면 로드맵의 필수 항목과 실제 근거를 대조해 작업 완료·단계 완료·사용자 수락을 구분합니다. 보고는 여섯 항목으로 핵심을 먼저 전하고, 판단에 필요한 원인과 검증 한계만 뒤에 설명합니다. 현재 코드·Git·실제 대상은 오래된 진행 설명보다 현재 상태의 근거가 되지만, 승인된 목표나 디자인을 자동으로 바꾸지는 않습니다.

## 사용법

### 1. 개인 도구 준비 — 한 번만

Windows PowerShell에서 이 저장소를 열고 현재 설치 상태를 확인합니다.

```powershell
powershell.exe -NoProfile -File .\JOENESS.ps1 -Check
```

`ready`라면 설치할 수 있습니다. `current`라면 같은 패키지가 이미 설치돼 있습니다. 설치할 때만 아래 명령을 실행합니다.

```powershell
powershell.exe -NoProfile -File .\JOENESS.ps1 -Apply
powershell.exe -NoProfile -File .\JOENESS.ps1 -Check
```

개인 설치는 `joeness-setup` 스킬과 설치 상태 파일 `joeness-skills-state.json`만 관리합니다. 전역 `AGENTS.md`나 개별 프로젝트 문서는 바꾸지 않습니다. 다른 설치 위치를 시험할 때는 **매 명령에** `-CodexHome <명시 경로>`를 붙입니다. 이전 설치 때문에 `blocked`가 나오면 [아래 안전 경계](#기존-설치와-충돌)를 따릅니다.

### 2. 새 프로젝트에 적용

1. Git 프로젝트를 Codex에서 열고 새 채팅에서 `이 프로젝트에 JOENESS 설치해줘.`라고 요청합니다. 이 요청은 **프로젝트 문서 연결**을 뜻하며 개인 도구를 다시 설치하라는 뜻이 아닙니다.
2. 제안된 문서 위치, 새로 만들 파일과 기록 범위를 확인합니다. 로드맵 역할의 기존 문서가 없으면 작은 `ROADMAP.md` 생성을 기본 제안합니다. 원하지 않으면 이때 제외할 수 있습니다. 다른 네 역할까지 일괄 생성하지 않으며, 제품 기준이나 디자인 승인 기록이 없다면 있다고 가정하지 않습니다.
3. 제안이 맞으면 `이대로 적용해줘.`라고 승인합니다. 적용 후 실제로 만든 파일, 수정한 파일, 연결만 한 기존 파일과 기록 범위를 보고받습니다.

Git이 없는 폴더는 자동으로 `git init`하지 않습니다. 현재 자동 연결 도구는 명시한 Git 루트와 UTF-8 파일을 대상으로 합니다. 비Git 폴더에는 변경안과 수동 적용 방법까지만 제시합니다.

### 3. 기존 프로젝트에 적용

1. 같은 문장으로 설정을 요청합니다. 에이전트는 현재 `AGENTS.md` 계층, Git 상태, 제품·계획·작업·문제·디자인 문서와 실제 경로를 먼저 확인합니다.
2. 기존 파일명과 내용을 우선 보존합니다. 로드맵 역할의 정본이 있으면 재사용하고, 없으면 `ROADMAP.md`를 기본 제안합니다. 다른 기록 문서는 자리가 실제로 없을 때만 제안합니다. 복잡한 문서를 자동 재편하거나 오래된 계획을 새 작업으로 만들지 않습니다.
3. 변경 파일과 기록 범위를 확인해 승인합니다. 긴 `AGENTS.md` 등으로 안전한 연결이 불가능하면 `blocked`를 보고하며, 기존 지침을 임의로 줄이거나 밀어내지 않습니다.

두 경로 모두 적용이 성공하면 프로젝트 `AGENTS.md`에는 짧은 `JOENESS-SETUP` 연결 구역이 들어갑니다. 파일이 없었다면 생성되고, 있었다면 승인된 구역만 추가됩니다. `.joeness/setup-state.json`은 그 구역의 적용 기준을 보관합니다. 이 상태 파일은 업무 기록이나 승인 증명이 아닙니다.

### 4. 문서 구조와 책임

아래 파일명은 **역할의 예시**입니다. 기존 프로젝트의 실제 이름과 경로를 사용하며, 모두 생성해야 하는 목록이 아닙니다.

| 역할 | 기록하는 내용 | 읽는 때 |
|---|---|---|
| `AGENTS.md` | 짧은 작업 안내, 원본 문서 위치, 동의한 기록 범위 | 프로젝트 작업을 시작할 때 |
| `ROADMAP.md` | 목표·순서·현재 단계·다음 가능 작업·필수 항목의 진입/완료 기준 | 새 작업·재개·단계 완료 판단 |
| `TASK.md` | 승인된 개별 작업의 진행·결과·검증·남은 일 | 진행 확인·인수인계 |
| `ISSUES.md` | 재발할 문제의 증상·원인·확인된 해결·우회책 | 문제 조사·재발 확인 |
| `DESIGN.md` | 디자인 원본·승인 범위와 미승인 부분 | 시각 작업·디자인 승인 충돌 |

기존 `PRODUCT.md` 등 제품 기준 문서는 별도 원본입니다. JOENESS가 여섯 번째 필수 파일로 생성하거나 `ROADMAP.md`로 대체하지 않습니다.

RACI는 **문서의 고정 서열이 아니라 사람의 책임**을 설명합니다.

- **수행(R):** 담당자나 AI가 승인된 작업을 실행하고 확인된 사실을 기록합니다.
- **결정(A):** 권한 있는 사용자·프로젝트 책임자가 목표·범위 변경과 사용자 수락을 결정합니다. 디자인 변경은 프로젝트가 정한 승인권자가 승인합니다.
- **참여(C):** 제품·디자인 담당자가 실제로 있을 때 관련 판단에 참여합니다.
- **공유(I):** 다음 담당자에게 확정 상태와 남은 일을 알립니다.

없는 담당자를 임의로 지정하거나 일상 기록마다 다시 승인을 요구하지 않습니다. 작업 담당자는 동의한 범위에서 작업 결과와 영향을 받은 로드맵 상태·다음 작업을 함께 갱신합니다. 문제 조사 담당자는 재사용할 원인·해결을 문제 문서에 남깁니다.

**원본은 역할별 한 곳.** 연결안에 정확한 파일·절을 지정합니다. 목표·완료 기준·현재 달성 상태는 로드맵 역할에서 함께 관리하고 작업 기록의 근거를 연결합니다. 같은 상태를 별도 체크리스트에 중복 관리하지 않습니다. 기존 문서 재편은 승인 후에만 진행합니다.

**기록은 처음부터 간결하게.** 필요한 결과·상태·근거 위치·남은 조건·다음 행동만 기록합니다. 원인·승인 범위·미확인 사실은 보존하고 반복 설명과 긴 로그는 원본으로 연결합니다. 글자 수 제한이나 매번 다시 요약하는 절차는 없습니다.

읽는 순서도 고정된 `1→5`가 아닙니다. 새 작업·재개는 현재 `ROADMAP` 단계와 `TASK`에서 시작하고, 문제 재발은 관련 `ISSUES`와 현재 구현을 대조합니다. 시각 작업은 승인된 `DESIGN`과 제품 기준을 확인합니다. 완료 판단은 현재 검증 결과와 로드맵의 필수 항목을 함께 확인합니다. 열린 진입 조건은 의존 작업만 막으며, 독립적으로 승인된 작업은 진행할 수 있습니다. 관계없는 문서는 매번 읽지 않습니다.

### 5. 평소 사용과 상태 확인

설정 뒤에는 평소처럼 `로그인 오류 고쳐줘.`, `남은 작업을 이어서 진행해.`, `이전 문제의 해결을 찾아봐.`라고 요청합니다. 매번 setup을 호출할 필요는 없습니다. 실제 작업 뒤에는 바뀐 파일, 해결한 문제, 남은 문제와 다음 일을 짧게 보고받습니다. 질문·의견만으로 문서를 갱신하지 않습니다. 이번 작업의 기록을 원치 않으면 `코드는 고치되 이번 작업은 문서에 기록하지 마.`라고 말할 수 있습니다.

개인 설치와 프로젝트 연결은 별개로 확인합니다.

```powershell
powershell.exe -NoProfile -File .\JOENESS.ps1 -Check
powershell.exe -NoProfile -File .\skills\joeness-setup\scripts\project-setup.ps1 -Check -ProjectPath <프로젝트-루트>
```

앞 명령의 `current`는 개인 도구, 뒤 명령의 `current/clean`은 해당 프로젝트의 연결 상태입니다. 연결 성공이 로드맵 내용까지 검증했다는 뜻은 아닙니다. 설정 완료 전 실제 문서의 현재 단계·완료 조건·다음 작업을 확인하고, 연결 뒤 새 채팅에서 실제 지침 전달을 확인합니다. 더 많은 요청 예시와 기록 중지·해제 방법은 [설치 후 사용 안내](skills/joeness-setup/references/usage.md)에 있습니다.

## 주의

### 기존 설치와 충돌

`blocked`는 덮어쓰지 않고 보존했다는 뜻입니다. 이름이 같은 스킬, 변경된 관리 파일, 이전 전역 Core 상태를 새 설치기로 강제 덮어쓰거나 상태 파일 삭제로 우회하지 않습니다. 기존 설치를 바꾸려면 정확히 대응하는 이전 패키지에서 `-Check: current`를 확인하고 **그 패키지의** `-Remove`를 실행한 뒤, 현재 패키지에서 `ready → Apply → current`를 확인합니다. 이전 소스나 소유 경계를 확인할 수 없으면 중단합니다. 개인 패키지 제거는 프로젝트 연결을 자동 해제하지 않습니다.

현재 패키지만 제거할 때는 `powershell.exe -NoProfile -File .\JOENESS.ps1 -Remove`를 사용합니다. `partial`이나 예상 밖 상태가 나오면 실제 대상 파일을 확인한 뒤 복구 범위를 판단합니다. 무조건 재시도하지 않습니다.

### 지원·검증 범위

JOENESS는 백그라운드 감시·자동 갱신기, 강제 정책 엔진, 디자인 스킬 호출기, 제품 계획 생성기가 아닙니다. 개인 도구 설치만으로 프로젝트 문서가 생기지는 않습니다. 프로젝트 연결에서는 로드맵 역할을 기본으로 제안하되 승인된 범위만 적용하며, 기존 자료를 무단 이동·삭제하지 않습니다. 현재 확인한 경로는 Windows PowerShell·Git·Codex 중심입니다. 모든 환경의 안정성이나 토큰 절감·일반 성능 향상은 입증되지 않았습니다.

[Superpowers](https://github.com/obra/superpowers)등의 스킬은 설계·계획·테스트 등 개발 절차 전반을 다루는 하네스입니다. JOENESS는 그런 절차를 강제하지 않고 프로젝트 문서의 기록 위치와 인수인계에 범위를 좁힙니다. [Codex 스킬](https://developers.openai.com/plugins/concepts/skills), [Claude Code 메모리](https://code.claude.com/docs/en/memory), [Cursor 규칙](https://cursor.com/docs), [Copilot 저장소 지침](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions-in-your-ide/add-repository-instructions-in-your-ide?tool=vscode)에도 관련 기능이 있으므로, JOENESS를 유일한 기억·지침 도구로 소개하지 않습니다. **기존 원본과 승인 경계를 프로젝트별로 연결하는 사용 방식**이 이 패키지의 특징이며, 다른 도구보다 정확하거나 빠르다는 비교 결과는 없습니다.

설치기의 JSON 결과는 stdout, 사람용 사용 안내는 stderr에 나옵니다. 자동화에서는 종료 코드와 JSON 상태를 확인합니다. 안내가 stderr에 있다는 이유만으로 실패로 판단하지 않습니다.

출시 결과는 [Windows 릴리스 검사](.github/workflows/windows-ci.yml), 설치 상태와 Git 태그로 확인합니다. 검증 근거와 알려진 한계는 [로드맵](docs/ROADMAP.md)과 `evals/joeness-setup/`에 남아 있습니다.
